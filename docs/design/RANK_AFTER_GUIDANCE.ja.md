# 順位付けを、決算の3本柱がそろってから行う（設計メモ）

作成: 2026-08-11。**User承認済み。2026-08-12 実装済み**
（`hawkeye scout` はゲート通過までで止まり、`hawkeye rank` が
`hawkeye/scout/scout.py` の `rerank_after_guidance()` で点数を計算し直して
から台帳に記録する。中間ファイルは `hawkeye/scout/scan_store.py` /
`var/scan/pending.json`）。1-d（API方式の承認済み停止点）は据え置き
— User判断: API方式は当面使わないため不要。

## 何が壊れているか

**同じ決算・同じ数字を入れても、動かし方を変えると審理に行く銘柄が変わります。**

決算の評価は3本柱（EPS・売上・**ガイダンス**＝会社が自分で出す次期の業績見通し）で
行うと決めています。ところが今の走査は、**3本目が空のまま順位を確定させています。**

| 動かし方 | ガイダンスを読むのは | 順位に入るか |
| --- | --- | --- |
| API方式（Anthropic APIキーで動かす） | 走査の中（`run_scout` の `guidance_reader`） | **入る** |
| セッション方式（`/hawkeye-run`） | 走査の**後**（`hawkeye guidance queue` / `submit`） | **入らない** |

セッション方式では、走査中からAIを呼ぶ経路がありません（`hawkeye scout` は
Claude Codeセッションが起動した子プロセスで、親にサブAgentを立てさせる手段が
無い）。そのため文章を `var/guidance/` に書き出し、走査はガイダンス欄を「未読」の
まま終わります。全銘柄が**ガイダンス0点**で順位が付き、そのあと読み取り結果が
決算行に載っても、**順位は付け直されません。**

### 大きさ（実測・2026-08-11・2日窓・使い捨てDB・標本1）

```
3位 ROKU 83.41  ← 審理に送られる
4位 BKV  78.75  ← 送られない        差 4.66点
```

ガイダンスの加点は最大5.0点（`guidance_beat_score`）。**逆転する幅にあります。**
「毎回ひっくり返る」とは言えません（標本1）。言えるのは幅だけです。

### なぜ許容できないか

1. CLAUDE.md は「両エンジンが同じ定数を読むことがAPI方式とセッション方式の結果を
   比較可能にしている」と書いています。選定ロジックが方式で変わるなら、その前提が
   消えます。
2. 3本柱の3本目が空のまま順位を決めるのは、**材料がそろう前の評価**です。

## 直し方

**走査中にAgentを入れるのではなく、順位付けを後ろに動かします。**

```
【今】 走査(数字→詳細取得→ゲート→順位確定→15枠→台帳記録) → ガイダンスを読む → 審理
                                    ↑ ここで3本目が空

【新】 走査(数字→詳細取得→ゲート→作業ファイルに保存)
       → ガイダンスを全件読む
       → 順位付け(3本柱そろった点数で並べ直し→15枠→台帳記録→レポート)
       → 審理
```

**API方式では、ガイダンスは走査中に決算行へ載っているので、順位付けの工程は同じ
コードで同じ答えを出します。順位付けの実装が1つになり、方式による差が消えます。**

### 却下した代替案

- **走査からAnthropic APIを直接叩く** — APIキーが要る。セッション方式はキー無しで
  動かすために存在しているので目的が消える。
- **走査から `claude -p` をコマンドとして呼ぶ** — LLM呼び出しがCLIの中に隠れる。
  統括セッションから見えず、どのモデルが読んだか追えず、情報分離が監査できない。
  審理の3役を見えるサブAgentとして立てている設計と逆行する。

## 実装の要点（ここを外すと要件が劣化する）

### 動かすのは1箇所だけ

`run_scout` の走査ループ（`hawkeye/scout/scout.py` 589-670行）が銘柄ごとにやって
いる9工程のうち、**順位に効くのは1つだけ**です。

| 工程 | 位置 |
| --- | --- |
| 決算行と物差しの組み立て（`_quarter_context`） | 走査に残す |
| ガイダンスの読み取り／待ち行列への書き出し（`_read_guidance`） | 走査に残す |
| 決算行の記録（`_record_print`） | 走査に残す |
| 詳細取得（`build_brief` — 株価・ニュース・インサイダー・アナリスト） | 走査に残す |
| 入口ゲート判定（`run_entry_gates`）と構造判定の記録（`record_triage`） | 走査に残す |
| 通過／落選の振り分け | 走査に残す |
| **点数の計算（`assess_earnings` — 値動き込み）** | **順位付けへ移す** |
| **並べ替え（`passed.sort`, 672行）** | **順位付けへ移す** |
| **台帳への記録（`record_scan` / `record_screened_candidates`）** | **順位付けへ移す** |

⚠️ **詳細取得の対象（どの銘柄を見るか）は走査に残します。** 走査ループの停止条件
（`scout_target_gate_passed` に達する／`scout_max_enrich` を使い切る）は、
ガイダンス以前のサプライズ順で歩く順序に依っており、**これは今も両方式で同じ**です。
ここを動かすと直したい差以外のものまで変わります。

### ⚠️ ガイダンスを出していない会社を待ってはいけない（User指示 2026-08-11）

**「3本柱がそろってから順位付け」の「そろう」は、「全銘柄がガイダンスを持つこと」では
ありません。** 会社が見通しを発表していなければ、**その銘柄はガイダンス分を考慮せず
（0点で）そのまま順位に入ります。**

実データで、決算専門サイトのサマリ文に見通しが1つも書かれていない銘柄は珍しく
ありません（47銘柄中27件という実測がある）。ここを「読み取り待ち」にすると、
**永久に来ない返事を待って順位付けが止まります。**

順位付け工程が待ってよいのは、**待ち行列に実際に積まれた案件だけ**です。
待ち行列（`hawkeye/scout/guidance_case.py`）に積まれるのは、決算専門サイトの
サマリ文が存在する銘柄だけで、文が無ければそもそも積まれません
（`_read_guidance` の冒頭 `if not event.summary: return context`）。
したがって「待ち行列が空になったら順位付けを実行してよい」という条件は、
**そのままで正しく、かつ必ず到達します。**

不在が0点であること自体は既存の規則（D-3）で、今回も変えません。
下振れの減点（`guidance_miss_penalty`）も**発表した会社にだけ**当たります。

### 2工程の間をどう渡すか

走査の結果（`ScoutResult`）を**作業ファイルに保存**し、順位付けが読みます。
`var/guidance/` や `var/cases/` と同じ方式で、置き場は `hawkeye/paths.py` に足します。

⚠️ **台帳に先に書いて後から書き換える形にしてはいけません**（不変条件1）。

### 落としてはいけないもの（走査が今やっていること）

順位付けへ移したあとも、以下は**全部**残ります。移設時の確認項目です。

- 保留（`held` — 決算の数値が未着）と打ち切り（`held_expired`）の判定
- 重複除去（`already_seen`）と、保留行を除外しない例外
- 実績値の訂正検出（`revisions`）と、順位表より前に出すこと
- 詳細取得に届かなかった銘柄（`capped`）の株価だけの記録
- 走査の停止理由の区別（`enrichment_ceiling_hit`）
- 決算行の安い記録（`_record_cheap_history`）と、保留中の決算を書かないこと
- 点検表（`build_inspection`）と5件数
- 遡り取得（`backfill_history` — 上位3銘柄の過去4四半期）
- 落選記録の全段階（`actual_pending` / `actual_timeout` / `enrichment_cap` /
  `gate_reject` / `ranking_cutoff`）
- 点数の内訳（`score_breakdown`）— **順位付け後の最終点数**を記録する（今は走査
  時点の点数、つまりガイダンス0点のものが入っている）

### 走査レポートへの影響

`hawkeye report scan` は順位付けの後に走るので、**ガイダンス0点の注記は不要になり
ます**（`hawkeye/reports/scan_report_ja.py` の `_breakdown_lines`）。
`SKILL.md` の手順は 2b（ガイダンス）→ **2c（順位付け・新設）** → 2d（レポート提示・
Userの承認待ち）→ 2e（審理）になります。

## 別件（この設計メモの範囲外・User判断待ち）

**ガイダンスの加点が「上回った幅」を見ていません。** `LegVerdict.beat_fraction` は
上回った項目の**数**を数えるだけで、アナリスト予想を+0.1%上回っても+30%上回っても
同じ5点です。これは囁き予想の加点を決めたとき（タスク8）に「段をまたぐと大きさが
無視される」という理由で**却下した段階式そのもの**で、同じ系の中で判断が矛盾して
います。点数の重みの変更なので不変条件7によりUserの承認が要ります。**未承認。**
