# Set H・Set G の判断記録(2026-08-13)

前セッションの引き継ぎメモ(`2026-08-12` 系セッション)が残した2つの未決事項
「Set H」(ランキングの精度を守る小さな2択)と「Set G」(決算前にコンセンサスを
記録しておく仕組み=**事前登録**の存廃)について、このセッションで下した判断と、
その根拠になった調査結果を記録する。ガバナンス規約(`CLAUDE.md` の
「Governance」節)に基づき、実装前にこの短い設計メモを書いている。

---

## Set H-1: ガイダンス下振れ判定の分母に下限を付ける

### 何が問題だったか

決算発表と同時に会社が出す業績見通し(以下「ガイダンス」)を、アナリスト予想
(コンセンサス)と比べて上振れ・下振れを判定する処理(`hawkeye/scout/quality.py`
の `_guidance_leg` 関数)には、比較に使う予想値(以下「物差し」)がゼロに近すぎて
比率が意味を持たなくなるケースへの歯止めが無かった。

EPS(1株あたり利益)とその上振れ率を判定する処理には、この歯止めが既にある
(`hawkeye/config.py` の `scout_min_abs_eps_estimate` = 0.10ドル)。REIT(不動産
投資信託)のようにGAAP(米国会計基準)のEPSがほぼゼロになる会社では、
+6958%のような数字が出てしまうためだ。しかしガイダンスの物差しには同じ歯止めが
無かった。実例: ALGTは「1株あたり1.00ドルの損失〜収支トントン」という見通しを、
0.08ドルのコンセンサスに対して出した。これは -725% にあたる。

### 今すぐ実害があるか

**採点への影響はまだ無い。** ガイダンスの下振れ減点(`guidance_miss_penalty` =
5.0点)は、下振れの大きさを読まず「下振れたか否か」だけを見る二値判定なので、
-725%でも-3%でも同じ5.0点しか引かれない。

ただし、**判定(上振れ/下振れ/横ばい)そのものへの影響は既にある。** この判定は
`_verdict` 関数(同ファイル)が「良い決算」かどうかを決めるのに使われ、審理
(Bull/Adversary/Judgeの3役による検討)にもそのまま渡る。物差しが信頼できない
水準でも「下振れ」という確定した事実として扱われてしまう。

### 決定

EPSの判定処理と同じ `scout_min_abs_eps_estimate` を、ガイダンスのEPS側の物差しにも
適用する。**新しい設定値は追加しない** — ガイダンスのEPS物差しも、通常のEPS
コンセンサスも同じ「EPSの予想値」という同じ種類の数字であり、既に測定済みの
下限をそのまま使うのが筋が通っている。売上側のガイダンスには適用しない(売上が
ゼロに近づくことは実務上ない — 既存のEPS/売上の判定処理と同じ非対称)。

物差しがこの下限を下回った場合、そのガイダンスの脚(EPS側)は上振れ・下振れの
集計から外し、`eps_yardstick_too_small` という理由フラグを付けて審理に渡す
(何も判定しなかったことを隠さない)。売上側だけで判定できるガイダンスは、
従来通り売上側だけで判定する。

## Set H-2: 使われなくなった「アナリスト人数が少なすぎる予想を無効化する規則」を削除する

### 経緯

決算のコンセンサス(アナリスト予想の平均値)が、実は1人のアナリストの意見
だけで作られていた場合に、その予想を「薄すぎて信頼できない」として無効化する
規則(`earnings_min_analysts` = 3人、`hawkeye/config.py`)が存在した。この規則は
INVH(コンセンサスがアナリスト1人分だけで構成されていた実例)への対応として
作られたもの。

**2026-08-06(既存の決定)**: 決算データの取得元をyfinance(Yahoo Finance)から
EW(EarningsWhispers、決算専門サイト)中心に切り替えるにあたり、「アナリスト
人数が失われることを受け入れる」という決定が既に下されている
(`docs/design/DATA_SOURCE_MATRIX.ja.md` §8-1)。EWのレスポンスにはアナリスト人数
が含まれておらず、この人数を返すのはyfinanceだけだった。

この決定の結果、コンセンサスを記録する処理(`hawkeye/scout/prereg.py` の
`capture_consensus` と、`hawkeye/scout/quality.py` の `reconstructed_consensus`)
の**どちらも、アナリスト人数の欄を一度も埋めていない**。つまり
`earnings_min_analysts` 規則が比較する相手(アナリスト人数)は**常に存在しない
(None)**状態になっており、規則を書いている条件文
(`hawkeye/scout/quality.py:223`)は2026-08-07以降、一度も真になったことが無い。

### 決定

死んだコード(`earnings_min_analysts` 設定値、それを比較する条件文、対応する
`thin_coverage` という理由フラグ)を削除する。理由:

1. 「アナリスト人数を失うことを受け入れる」という判断は既に確定済みで、今回
   新しく判断することは無い。今回やるのは、確定済みの判断をコードに反映する
   後片付けだけ。
2. アナリスト人数の欄(`ConsensusSnapshot.eps_analysts` / `revenue_analysts`)
   自体は契約(データモデル)には残す。将来、別の取得元から人数を取れるように
   なった場合に備えるのではなく(それはやらないと決めた選択肢②)、単に
   この欄を削ると影響範囲が契約全体・DBスキーマ・8個以上のテストファイルに
   広がり、今回の後片付けの範囲を超えるため。
3. `LegVerdict.analysts` という表示用の欄(「N人のアナリスト」という表示に使う)
   もそのまま残す。これも常にNoneになるが、表示コードは既に「値がある時だけ
   表示する」処理になっており、削除する理由が無い。

対象外(今回は変更しない): `docs/design/DATA_SOURCE_MATRIX.ja.md` §8-1に書かれた
「EWが人数を返すかは未確認」という調査項目そのもの。今回はこの規則を使う側の
死んだコードを消すだけで、EWから人数を取得する新しい仕組みを作る話ではない。

## Set G: 決算前のコンセンサス記録(事前登録)の存廃

### 問題の立て方

決算が発表される**前**に、その時点のアナリスト予想を記録しておく仕組み
(以下「事前登録」、`hawkeye/scout/prereg.py`、`hawkeye consensus capture`
コマンドで手動実行)がある。前セッションまでに次の実測が揃っていた
(`docs/knowledge/MEASUREMENTS.ja.md`):

- 決算前に記録した153件のうち136件(88.9%)は、決算後に同じ問い合わせ窓口
  (EW)へもう一度聞いても数字が変わっていなかった
- 変わった17件のうち12件は、予想EPSの絶対値が0.15ドル未満の銘柄(小さすぎる
  分母のせいで率が揺れて見えるだけの可能性が高い、`scout_min_abs_eps_estimate`
  の閾値0.10ドルに近い水準)
- 「動いた」がアナリストの本当の予想改定なのか、単に2回の問い合わせが元々
  ズレていただけなのかは、この実測では切り分けられていない、という留保付き

前セッションの引き継ぎメモは、この問いを「事前登録という仕組みそのものを畳んで、
決算後にEWが返す値をそのまま使い、差分がどの程度実害になるかを次の四半期
サイクルで様子見する、という選択肢はないか」という形で次セッションに残していた。

### 今回追加で調べたこと

**事前登録が本来必要だった理由は、既に別の変更で解消されている。**
`docs/design/MASTER_OVERVIEW.ja.md` §5.3(8)①によれば、事前登録を作った最大の
根拠は「Yahoo Financeの予想取得エンドポイントは、決算が終わった後に読むと
1四半期分ズレた数字を返す」というバグだった(AMZNの実例: 決算3日後に読むと
1.956だったが、その決算が実際に比較された予想は1.83で、成長率を見ると別の
四半期の数字だった)。**このYahooエンドポイントは2026-08-09に別の理由(ガイダンス
の読み取り方法をEWの要約文に切り替えたこと)で、コード自体が削除されている。**

現在、決算後にコンセンサスを再構成する処理(`hawkeye/scout/quality.py` の
`reconstructed_consensus` 関数)は、EWが決算の要約文の中で述べる「次四半期は
いくら」「通期はいくら」という予想を直接読み取っている
(`hawkeye/scout/numbers.py` の `_forward_legs`)。これはYahooの「決算後に読むと
別の四半期を指す」問題を最初から持たない経路 — EWの要約文は発表と同時に
その決算についての文章として生成されるため、後から読んでも指している四半期は
ズレない。

**加えて、コードは既に「事前登録が無い決算」を無言で正しく処理する。**
`hawkeye/scout/scout.py` の `_quarter_context` 関数は、事前登録された行が
無い銘柄・四半期の組み合わせに出会うと、その場で決算後の数字から
`reconstructed_consensus` を組み立てて使う(56-63行目のロジック)。この経路は
既にテストされており、事前登録を1件も実行しなかったとしても、走査
(`hawkeye scout`)は今と同じ形で動く。両者の違いは記録に残る「出所」の表示
(`quality_ja.py` が「(pre_registered)」か「(reconstructed)」かを表示に出す)
だけで、採点や入口ゲートの判定を変える分岐はどこにも無い。

**もう1つ、独立した裏付けが既に測定済みだった。** ガイダンス(会社自身の見通し)の
物差しには、Yahooの四半期ズレとは別の汚染リスクが理屈の上ではありえた —
「決算後に翌四半期コンセンサスを読むと、アナリストが既にガイダンスに反応して
予想を修正した後の数字を読んでしまい、上振れの差がほぼゼロに潰れる」という懸念
(`docs/design/DATA_SOURCE_MATRIX.ja.md` §8.1)。この懸念に対しては、EWが決算の
数分後に書く要約文がその後**書き換わらない**ことが既に実測されている
(2026-08-06実測: 確定した決算6件を翌日に引き直して5件が完全一致)。つまり
「いつ読むか」で数字が変わらない — 事前登録の有無に関わらず、この物差しは
決算直後の値のまま凍っている。

### 決定: 事前登録を「毎日必ず回す作業」から外す。コード・台帳・テストは削らない

前セッションの引き継ぎが挙げていた3択のうち、いずれでもない第4の選択肢を取る:

| 選択肢 | 今回の判断 |
| --- | --- |
| ①存続(現状維持) | 採らない — 手動での毎日実行という運用コストを払い続ける理由が、上記の調査で薄くなった |
| ②廃止(コード・コマンド・テーブル・テストを削る) | 採らない — 17件の「動いた」の原因(本当の予想改定か、単なる測定誤差か)が未解決のまま、遡れない形で仕組みを壊すのは早すぎる。台帳に残る153件超の記録も、その調査に使える資料である |
| ③深追い(17件を1件ずつ手動確認してから決める) | 今回はやらない — 上記の技術的な調査(Yahooバグの解消・無言フォールバックの存在確認)だけで、「事前登録を毎日回す理由」の大部分は既に無くなっていることが分かったため、17件の手動確認を待たずに運用を止める判断ができる |
| **④(今回の決定)運用の必須リストから外す。コードはそのまま残す** | **採用** |

具体的にやること:

1. `hawkeye consensus capture` を「決算シーズン中は毎営業日回してください」と
   書いていた運用上の指示(`docs/design/MASTER_OVERVIEW.ja.md` §5.3(8))を、
   「原則不要。決算後の再構成が既定の経路になった」という記述に書き換える
2. `docs/knowledge/MEASUREMENTS.ja.md` の88.9%の実測に、この決定へのリンクを
   注記として追加する
3. `hawkeye/scout/prereg.py`・`hawkeye consensus capture` コマンド・
   `hawkeye consensus drift` コマンド・関連テーブル・関連テストは**一切削除
   しない**。事前登録は「使いたい時に使える機能」として残す — 例えば、
   ③の深追い調査(17件の手動確認)を将来やりたくなった場合や、特定の銘柄
   だけ手厚く記録したい場合に、そのまま使える

### この決定の可逆性

コードを1行も削除しないため、この決定は**完全に可逆**である。もし
「reconstructed(決算後の再構成)だけに頼るようになってから成績が落ちた」と
分かれば、`hawkeye consensus capture` を再び毎日回す運用に戻すだけでよい。
逆に、この決定が正しければ、次の決算シーズンを迎えるたびに「今日は事前登録を
回し忘れた」という前セッションまで抱えていた運用リスクが消える。
