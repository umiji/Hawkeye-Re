## /hawkeye-runを実行したときのフロー概要

### 0. 走査の前準備（フロー図に無いが走っている）

- 前回の走査記録から**今回の窓を決める**
- 発表文の読み取り待ちのうち、決算から日が経ちすぎたものを打ち切る

**テーブル操作**

| テーブル | 操作 |
| --- | --- |
| `scans` | **読む** — 前回の窓の終わりが今回の起点 |
| `release_requests` | **読む＋更新** — 期限切れを打ち切り、生きているものを取り出す（移で廃止） |
| `screened_candidates` | **読む** — 過去に見た決算の一覧（ステップ5の重複除去に使う） |

**テーブル操作: なし。** 外部APIを叩くだけ。

### 2. スクリーン1回目（暫定）
EPSサプライズが閾値以上、売上サプライズも閾値以上（データがあれば）の銘柄だけ残し、スコア順に並べる。
    * 生のサプライズ率順ではありません。2026-08-01の走査が +6958% / +5194% / +3459% という読みに占領され、ほぼ全部REITだったためです（コンセンサスがゼロ近傍だと比率が意味を失う）。上限付きのスコアで並べることで、信用できない％が上位ではなく最下位に沈むようにしてあります。

|項目 | 　あなたの理解 | 　実際 |
|-----|-----------------|-------|
| EPSサプライズ | >= +5.0% | ✅ 正しい（scout_min_eps_surprise_pct = 5.0） |
| 売上サプライズ | >= 0.0% | ⚠️ 売上データがある場合のみ。無い銘柄は落とさない |
| EPS点数の上限 | 50点 | ✅ ただし対称。−50点まで減点される |
| 売上点数の上限 | 20点 | ⚠️ サプライズ率を2倍してから20点で頭打ち。かつプラスのときだけ加算（マイナスは減点されない） |
| EPS予想| < $0.10 | untrusted・加点0 |	✅ 正しい
| 売上サプライズ > 50% | untrusted・加点0 | ✅ 正しい |

**テーブル操作: なし。** メモリ上の計算だけ。

### 4. スクリーン2回目（本番）
EWの数字でスクリーンし直し、並べ直す。この順位が本番です。
    2回スクリーンする理由がコメントに残っています —「順位を決める指標そのものが壊れていると、誰を検証するかの選択も壊れる」。検証を順位付けの後にすると、壊れた指標で選んだ相手しか検証できません。

**テーブル操作: なし。**

---

### 5. 重複除去
走査の窓は重なるので、前回すでに見た決算を除きます。

**何の重複か: 走査対象の重複。** DBの行の重複ではない。窓が過去7日なので、毎日走らせると
**6日分が前回と重なる**。同じ決算イベント（銘柄＋発表日）が何度もカレンダーに出てくる。
再評価すると無料枠の呼び出しを無駄にし、落選記録に同じ銘柄が何度も入って統計が狂う。

**ステップ0と5は同じ1つの仕組みの前半と後半**:
- ステップ0 = 過去に見た決算の一覧を**読んでくるだけ**
- ステップ5 = その一覧と突き合わせて**実際に除く**

**テーブル操作**

| テーブル | 操作 |
| --- | --- |
| `screened_candidates` | **読む**（ステップ0で読んだ一覧と突き合わせ） |
| `release_requests` | **読む** — 1つだけ例外があり、発表文を依頼済みの決算は重複除去から**除外しない**。除外すると、頼んだ資料を誰も読まないまま終わる（2026-08-03に発見） |

**移**: 発表文の依頼が無くなるので、この例外ごと消える。

### 6. 上から順に enrichment → ゲート判定のループ

ここが重要です。上位15件を切り出しているのではありません。


順位1位から順に:
  - 株価・出来高・イベント日の反応を取得（enrichment）
  - ゲート判定（Penny株、流動性など）
  - 通ったら passed に追加

  passed が 15 件（scout_target_gate_passed）に達したら終了
  または 試行が 45 件（scout_max_enrich）に達したら終了
「ゲートを通ったものを15件集める」方式です。上位15件のうち14件がゲートで落ちた日に、16位以下を一切試さず1銘柄しか審理に送らなかった事故（2026-08-02）があって、その対策です。45件の上限は「今日は悪い日だ」と判断して止めるための天井です。

**テーブル操作 — ここが書き込みの本体。1銘柄ごとに以下が走る**

| 順 | テーブル | 操作 |
| --- | --- | --- |
| 1 | `stocks` | **読む→無ければ書く** — ティッカーからCIKを引いてマスタ行を作る。既存行があればそれを使う |
| 2 | `consensus_snapshots` | **読む** — この四半期の事前登録があるか探す |
| 3 | `consensus_snapshots` | **無ければ書く** — 事後再構成のコンセンサス（`kind=reconstructed`）。「発表前に知り得た値」とは決して混ぜない |
| 4 | `earnings_prints` | **読む** — 同じ四半期の行が既にあるか |
| 5 | `earnings_prints` | **書く** — 当期の決算行。既存行より深ければ追記、同じか浅ければ**黙って何もしない** |

**ここでの「深さ」= `depth` カラム**（`calendar_only` < `verified`）。同じ四半期でも、より深い
読みが得られたら新しい行を追記する。同じか浅い読みは情報を足さないので捨てる。

⚠️ **保留行を書いてはいけない理由は、`depth` を消すかどうかで入れ替わる（結論は同じ）**

- **現の定義**（`verified` = 2ソース照合できた）: 実績が届いても照合できなければ
  `calendar_only` のまま。保留行を先に書くと、後から届いた実績も同じ深さで捨てられる
- **移の定義**（`verified` = 当期のレコードで実績の実在を確認）だけなら、
  `calendar_only` → `verified` で深くなるので**普通に追記できてしまう**。この理由は消える
- **`depth` を削除すると（合意済み）**「1四半期1行」になるので、保留行を先に書くと
  実績行が書けなくなる。**保留行を書かない規則は depth 削除とセットで改めて必要**

- **現**: この途中で発表文の読み取りが割り込む（2ソースの実績が食い違った銘柄のみ）
- **移**: 割り込みごと削除

### 7. 最終ソートと3枠
passed をスコア降順に並べ、上位3件が審理へ。残り12件は落選記録()に「順位カットオフ」として理由付きで残ります。

**テーブル操作**

| 順 | テーブル | 操作 |
| --- | --- | --- |
| 1 | `earnings_prints` | **書く** — 下記「履歴の書き込み」を参照 |
| 2 | `consensus_snapshots` | **書く** — 上の履歴行に対応する事後再構成 |
| 3 | `scans` | **書く** — 今回の窓・件数・通過銘柄。**次回の走査の起点になる** |
| 4 | `screened_candidates` | **書く** — 落ちた全銘柄を段階別に記録（スクリーン落ち／ゲート落ち／順位カットオフ／重複） |
| 5 | `release_requests` | **書く** — 発表文の依頼（移で廃止） |

⚠️ **3の `scans` はカレンダーが読めなかったときには書かない。** 誰も読めなかった窓を「走査済み」として記録すると、その日の決算が永久に手の届かない場所に行く（2026-08-03に本番で発生）。

#### 履歴の書き込み（1の中身）— 遡り取得ではない

名前は「履歴」だが、**過去に遡って穴を埋める機能ではない**。実際にやっているのは:

- 対象は**今回のカレンダー応答（過去7日分）に入っている決算だけ**
- そのうち **①スクリーンを通った銘柄 または ②すでに銘柄マスタに載っている銘柄**の分を書く
- 追加のAPI呼び出しはゼロ（カレンダー応答に既に入っていた数字を使う）
- 同じ四半期の行が既にあればスキップ

つまり「**候補にはならなかったが、うちがフォローしている銘柄の決算も記録しておく**」処理。
毎日走らせれば四半期ごとに履歴が積み上がる、という意味であって、遡りはしない。
EWが最新1決算しか返さないこととは無関係。

### 8. 審理（上位3枠）

**テーブル操作**

| テーブル | 操作 |
| --- | --- |
| `recommendations` | **書く** — BUY提案。**書き換え不能** |
| `journal` | **書く** — ハッシュ連鎖された追記記録 |
| `stocks` | **更新** — 「最後にいつ・どの四半期を・どこまで審査したか」の射影 |
| `earnings_prints` | **読む** — 案件を開く時点で決算行とコンセンサスを引き、触媒テキストと構造化ファクトを組み立てる |
| `consensus_snapshots` | **読む** — 同上 |

⚠️ **`case open --from-earnings`（走査を経ず単一銘柄を審理にかける経路）は決算行を書く。**
`judge_ticker` → `_record_print`。走査がやっているのと同じ「決算を記録する」処理を
ここで実行している。

守るべき性質は「審理は決算数値を書かない」ではなく、正しくは:

> **3役の結論は決算行に書き戻らない。**

案件を**開く準備**として決算を取得・記録するのは走査と同じ処理で、問題ない。禁じるべきは
「審理した結果で決算の数字が変わる」こと。

**3役自身はDBを引かない。** Bull・Adversary・Judge が見るのは渡されたパッケージだけ
（情報分離・不変条件4）。

## 別サイクルで走るもの（このフローには入らない）

### 事前登録 — `hawkeye consensus capture`（決算の**発表前**）

Finnhubカレンダーから今後N営業日の決算予定を取り、コンセンサスを記録しておく。

| テーブル | 操作 |
| --- | --- |
| `stocks` | 読む→無ければ書く |
| `earnings_prints` | **読む** — 既に発表済みならスキップ |
| `consensus_snapshots` | **書く**（`kind=pre_registered`） |

なぜ発表前に要るか: **コンセンサスには一次資料が世界のどこにも存在しない。** 発表後、ベンダーは予想値を次期のものに差し替える。記録しておかないと「発表前に何が期待されていたか」は永久に復元できない。
