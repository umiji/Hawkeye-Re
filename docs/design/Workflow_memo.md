### 2. スクリーン1回目（暫定）
EPSサプライズが閾値以上、売上サプライズも閾値以上（データがあれば）の銘柄だけ残し、スコア順に並べる。
    * 生のサプライズ率順ではありません。2026-08-01の走査が +6958% / +5194% / +3459% という読みに占領され、ほぼ全部REITだったためです（コンセンサスがゼロ近傍だと比率が意味を失う）。上限付きのスコアで並べることで、信用できない％が上位ではなく最下位に沈むようにしてあります。

### 5. 重複除去
走査の窓は重なるので、前回すでに見た決算を除きます。

**何の重複か: 走査対象の重複。** DBの行の重複ではない。窓が過去7日なので、毎日走らせると
**6日分が前回と重なる**。同じ決算イベント（銘柄＋発表日）が何度もカレンダーに出てくる。
再評価すると無料枠の呼び出しを無駄にし、落選記録に同じ銘柄が何度も入って統計が狂う。

**ステップ0と5は同じ1つの仕組みの前半と後半**:
- ステップ0 = 過去に見た決算の一覧を**読んでくるだけ**
- ステップ5 = その一覧と突き合わせて**実際に除く**

**テーブル操作**

| テーブル | 操作 |
| --- | --- |
| `screened_candidates` | **読む**（ステップ0で読んだ一覧と突き合わせ） |
| ~~`release_requests`~~ | 🗑️ **【済】例外ごと消滅**（2026-08-07） |

**【済】** 発表文の依頼が無くなったので、例外は消えました。
⚠️ ただし **48時間の実績待ち（タスク6）を作るときに、同じ形の例外がもう一度必要**
です。保留中の決算を重複除去が弾くと、実績が届いても二度と読まれません
（2026-08-03に発見した「書類は用意されるが誰も読まない」と同じ罠）。

### 6. 上から順に enrichment → ゲート判定のループ

ここが重要です。上位15件を切り出しているのではありません。


順位1位から順に:
  - 株価・出来高・イベント日の反応を取得（enrichment）
  - ゲート判定（Penny株、流動性など）
  - 通ったら passed に追加

  passed が 15 件（scout_target_gate_passed）に達したら終了
  または 試行が 45 件（scout_max_enrich）に達したら終了
「ゲートを通ったものを15件集める」方式です。上位15件のうち14件がゲートで落ちた日に、16位以下を一切試さず1銘柄しか審理に送らなかった事故（2026-08-02）があって、その対策です。45件の上限は「今日は悪い日だ」と判断して止めるための天井です。

**テーブル操作 — ここが書き込みの本体。1銘柄ごとに以下が走る**

| 順 | テーブル | 操作 |
| --- | --- | --- |
| 1 | `stocks` | **読む→無ければ書く** — ティッカーからCIKを引いてマスタ行を作る。既存行があればそれを使う |
| 2 | `consensus_snapshots` | **読む** — この四半期の事前登録があるか探す |
| 3 | `consensus_snapshots` | **無ければ書く** — 事後再構成のコンセンサス（`kind=reconstructed`）。「発表前に知り得た値」とは決して混ぜない |
| 4 | `earnings_prints` | **読む** — 同じ四半期の行が既にあるか |
| 5 | `earnings_prints` | **書く** — 当期の決算行。**その四半期に有効な行が既にあれば黙って何もしない** |

**【済】2026-08-07 変更。「深さ」（`depth`）は無くなりました。** いまは
**1つの四半期に有効な行は常に1つ**（`status='active'`）で、行が増える理由は
**「実績が改訂された」の1種類だけ**です。改訂のときは新しい行を `active` で追加し、
古い行を `superseded` に落として**残します**（順位を付けた時点でどの値を見ていたかが
消えないため）。SQLiteの一意インデックスは `active` の行だけを対象にした部分
インデックスなので、退避済みの行がいくつ積まれても新しい改訂を邪魔しません。

なお走査（この経路）は改訂を拾いません。同じ四半期の行が既にあれば何もしないだけです。
**改訂を検出してユーザーに差分を見せるのはタスク8.5**（48時間再取得）の仕事で、まだ
実装されていません。

⚠️ **保留行を書いてはいけない理由**（結論は前から変わらず、根拠だけ確定しました）

- 昔の理由は「深さが同じだと後から届いた実績が捨てられる」でしたが、`depth` が
  無くなったので**この言い方はもう成立しません**
- 新しい理由は**「1四半期1行」だから**です。実績が無い状態で保留の行を先に書くと、
  その四半期は「行がある」状態になり、48時間後に実績が届いても走査は何もしません
- したがって **保留は決算行に書かず、落選記録に `stage="actual_pending"` として
  積む**（タスク6）

- ~~**現**: この途中で発表文の読み取りが割り込む（2ソースの実績が食い違った銘柄のみ）~~
- 🗑️ **【済】割り込みごと削除**（2026-08-07）

#### 履歴の書き込み（1の中身）— 遡り取得ではない

名前は「履歴」だが、**過去に遡って穴を埋める機能ではない**。実際にやっているのは:

- 対象は**今回のカレンダー応答（過去7日分）に入っている決算だけ**
- そのうち **①スクリーンを通った銘柄 または ②すでに銘柄マスタに載っている銘柄**の分を書く
- 追加のAPI呼び出しはゼロ（カレンダー応答に既に入っていた数字を使う）
- 同じ四半期の行が既にあればスキップ

つまり「**候補にはならなかったが、うちがフォローしている銘柄の決算も記録しておく**」処理。
毎日走らせれば四半期ごとに履歴が積み上がる、という意味であって、遡りはしない。
EWが最新1決算しか返さないこととは無関係。

### 8. 審理（上位3枠）

**テーブル操作**

| テーブル | 操作 |
| --- | --- |
| `recommendations` | **書く** — BUY提案。**書き換え不能** |
| `journal` | **書く** — ハッシュ連鎖された追記記録 |
| `stocks` | **更新** — 「最後にいつ・どの四半期を・どこまで審査したか」の射影 |
| `earnings_prints` | **読む** — 案件を開く時点で決算行とコンセンサスを引き、触媒テキストと構造化ファクトを組み立てる |
| `consensus_snapshots` | **読む** — 同上 |

⚠️ **`case open --from-earnings`（走査を経ず単一銘柄を審理にかける経路）は決算行を書く。**
`judge_ticker` → `_record_print`。走査がやっているのと同じ「決算を記録する」処理を
ここで実行している。

守るべき性質は「審理は決算数値を書かない」ではなく、正しくは:

> **3役の結論は決算行に書き戻らない。**

案件を**開く準備**として決算を取得・記録するのは走査と同じ処理で、問題ない。禁じるべきは
「審理した結果で決算の数字が変わる」こと。

**3役自身はDBを引かない。** Bull・Adversary・Judge が見るのは渡されたパッケージだけ
（情報分離・不変条件4）。
