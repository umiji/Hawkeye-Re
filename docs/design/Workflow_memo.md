### 4.5. 実績が届いていない決算を保留にする 【済】

EWが**前期のレコード**を返した決算、EWに**接続できなかった**決算、
そしてFinnhubカレンダーが同じ決算に**矛盾する実績値**を返した決算は、
順位に載せずに保留します（`hawkeye/scout/waiting.py`）。

⚠️ **カレンダーの数字で順位を付けて通してはいけません。** 通した瞬間に決算行が
書かれ、次回以降の重複除去がその決算を弾き、**EWの数字は二度と読まれません**。
その銘柄は永久にカレンダーの物差しで判断され、記録にその事実も残りません。

- 保留は**詳細取得の前**に分けるので、API呼び出しは1回も使いません
- 起点は**Finnhubカレンダーの決算予定日**。EWの発表時刻ではありません
  （保留中は前期のレコードが返っているので、その時刻は前四半期のもの）
- 48時間（`earnings_actual_wait_hours`）を過ぎたら打ち切り

**保留にしないもの**: EWに記録が無い／実績かコンセンサスが欠ける／より新しい
決算を返す／HTTP 500（銘柄ごとに決定論的）。どれも待っても変わらないので、
**決算まるごとカレンダーの数字**に切り替えて順位に載せます。

**テーブル操作**

| テーブル | 操作 |
| --- | --- |
| `screened_candidates` | **書く**（ステップ7で） — `stage="actual_pending"` を1走査につき1行。期限切れは `actual_timeout` |
| `earnings_prints` | **書かない** — 保留中に行を書くと「その四半期は記録済み」になり、実績が届いても走査が何もしなくなる |

### 5. 重複除去 【済・位置が変わりました】

> ⚠️ **2026-08-08 に位置が変わりました。** いまは**ステップ2の直後**、EWに
> 問い合わせる**前**に走ります。以前はステップ5（EW取得の後）にあり、
> 窓7日・毎日実行なら**約85%が無駄打ち**になっていました。
> この節は「何をしているか」の説明として残しています。

走査の窓は重なるので、前回すでに見た決算を除きます。

**何の重複か: 走査対象の重複。** DBの行の重複ではない。窓が過去7日なので、毎日走らせると
**6日分が前回と重なる**。同じ決算イベント（銘柄＋発表日）が何度もカレンダーに出てくる。
再評価すると無料枠の呼び出しを無駄にし、落選記録に同じ銘柄が何度も入って統計が狂う。

**ステップ0と5は同じ1つの仕組みの前半と後半**:
- ステップ0 = 過去に見た決算の一覧を**読んでくるだけ**
- ステップ5 = その一覧と突き合わせて**実際に除く**（実行位置はステップ2の直後）

**同じ地点で、過去にトリアージで落ちた会社も除きます**（§6.1(E)）。
株価・時価総額・出来高は1銘柄ごとの有料API呼び出しでしか分からないので、
ゲートそのものを先に置くことはできません。代わりに、**過去の走査でゲートが
出した会社についての判定**（ステップ6の6で書いたもの）をマスタから読みます。

```
選別を通った銘柄ごとに stocks を引く
  ├ マスタに行が無い                    → 問い合わせる（判定が無い＝除外しない）
  ├ investigation_target が True か未判定 → 問い合わせる
  ├ False かつ判定日が90日以内            → ★除く（EWのリクエストを1回節約）
  └ False だが判定日が90日超              → 問い合わせる（判定が失効）
```

**迷ったら必ず問い合わせる側に倒します。** 間違って除外すると、その決算の
コンセンサスは二度と取れません（決算後にベンダーが次期の値に差し替えるため）。
間違って含めてもAPI呼び出しが1回無駄になるだけです。

⚠️ **現時点では1銘柄も除きません。** 理由は3つ重なっています:
1. 本番の台帳を作り直したため `stocks` が0行で、判定が1つも存在しない
2. 判定が付くのは1回の走査で最大45銘柄（ゲートに到達した分）だけ
3. その会社が次に決算を出すのは約91日後。**四半期単位で効いてくる仕組み**

⚠️ **有効期限の設定に疑義があります（2026-08-08 発見・未決）。**
`stock_triage_ttl_days = 90` のコメントは「およそ2決算期」と書いていますが、
90日は**約1決算期**です。決算間隔が約91〜92日なので、判定は次の決算が来る
直前に失効し、**この除外はほぼ毎回「ちょうど失効した状態」で使われます**。
意図どおりにするなら180日。安全側（除外しすぎない）に倒すなら現状維持。
判断待ちです。

### 6. 上から順に enrichment → ゲート判定のループ

ここが重要です。上位15件を切り出しているのではありません。


順位1位から順に:
  - 株価・出来高・イベント日の反応を取得（enrichment）
  - ゲート判定（Penny株、流動性など）
  - 通ったら passed に追加

  passed が 15 件（scout_target_gate_passed）に達したら終了
  または 試行が 45 件（scout_max_enrich）に達したら終了
「ゲートを通ったものを15件集める」方式です。上位15件のうち14件がゲートで落ちた日に、16位以下を一切試さず1銘柄しか審理に送らなかった事故（2026-08-02）があって、その対策です。45件の上限は「今日は悪い日だ」と判断して止めるための天井です。

**テーブル操作 — ここが書き込みの本体。1銘柄ごとに以下が走る**

| 順 | テーブル | 操作 |

#### 6の中身 — ここが「過去に落ちた会社を除く」判定の発生源（§6.1(E)）

ステップ5で読む判定は、**ここで書かれたもの**です。書く側と読む側が
1回の走査の中で離れているので、対応を明示します。

- **書く条件**: 3条件のうち**判定できたものが1つ以上**あること。データが取れず
  未検証だった条件は使いません（欠測を永久除外に変えないため）。1つも判定
  できなければ**何も書きません**（＝「意見なし」＝次回も問い合わせる）
- **`max_event_age_days`（決算からの経過日数）は使いません。** 硬い関門ですが
  *その決算*についての事実であり、それで会社を除外すると「見るのが遅れただけ」の
  優良企業を永久に落とします
- **数値（株価・時価総額・売買代金）はマスタに書きません。** 可変の観測値を
  マスタに置くと、後から分析するときに「判断した時点では知り得なかった値」を
  読めてしまうためです。数値は落選記録（`screened_candidates.gate_report`）と
  推奨記録に、その時点の値のまま凍結されます
- **判定は射影**なので、`hawkeye stocks rebuild` で落選記録から作り直せます

⚠️ **効き始めるまでに四半期単位の時間がかかります。** 判定が付くのは1回の走査で
最大45銘柄（ゲートに到達した分だけ）で、その会社が次に決算を出すのは約91日後です。
日次で積み上がる種類の効き目ではありません。

**【済】2026-08-07 変更。「深さ」（`depth`）は無くなりました。** いまは
**1つの四半期に有効な行は常に1つ**（`status='active'`）で、行が増える理由は
**「実績が改訂された」の1種類だけ**です。改訂のときは新しい行を `active` で追加し、
古い行を `superseded` に落として**残します**（順位を付けた時点でどの値を見ていたかが
消えないため）。SQLiteの一意インデックスは `active` の行だけを対象にした部分
インデックスなので、退避済みの行がいくつ積まれても新しい改訂を邪魔しません。

なお走査（この経路）は改訂を拾いません。同じ四半期の行が既にあれば何もしないだけです。
**改訂を検出してユーザーに差分を見せるのはタスク8.5**（48時間再取得）の仕事で、まだ
実装されていません。

⚠️ **保留行を書いてはいけない理由**（実装済み。根拠は下記）

- 昔の理由は「深さが同じだと後から届いた実績が捨てられる」でしたが、`depth` が

  その四半期は「行がある」状態になり、48時間後に実績が届いても走査は何もしません

  積む** 【済・`b1fac2e`】。四半期履歴の穴埋め（下記ステップ7）も保留中の決算は
  飛ばします — そこで行を書くと同じ罠に落ちるため

#### 履歴の書き込み（1の中身）— 遡り取得ではない

名前は「履歴」だが、**過去に遡って穴を埋める機能ではない**。実際にやっているのは:

- 対象は**今回のカレンダー応答（過去7日分）に入っている決算だけ**
- そのうち **①スクリーンを通った銘柄 または ②すでに銘柄マスタに載っている銘柄**の分を書く
- 追加のAPI呼び出しはゼロ（カレンダー応答に既に入っていた数字を使う）
- 同じ四半期の行が既にあればスキップ

つまり「**候補にはならなかったが、うちがフォローしている銘柄の決算も記録しておく**」処理。
毎日走らせれば四半期ごとに履歴が積み上がる、という意味であって、遡りはしない。
EWが最新1決算しか返さないこととは無関係。

### 8. 審理（上位3枠）

**テーブル操作**

| テーブル | 操作 |
| --- | --- |
| `recommendations` | **書く** — BUY提案。**書き換え不能** |
| `journal` | **書く** — ハッシュ連鎖された追記記録 |
| `stocks` | **更新** — 「最後にいつ・どの四半期を・どこまで審査したか」の射影 |
| `earnings_prints` | **読む** — 案件を開く時点で決算行とコンセンサスを引き、触媒テキストと構造化ファクトを組み立てる |
| `consensus_snapshots` | **読む** — 同上 |

⚠️ **`case open --from-earnings`（走査を経ず単一銘柄を審理にかける経路）は決算行を書く。**
`judge_ticker` → `_record_print`。走査がやっているのと同じ「決算を記録する」処理を
ここで実行している。

守るべき性質は「審理は決算数値を書かない」ではなく、正しくは:

> **3役の結論は決算行に書き戻らない。**

案件を**開く準備**として決算を取得・記録するのは走査と同じ処理で、問題ない。禁じるべきは
「審理した結果で決算の数字が変わる」こと。

**3役自身はDBを引かない。** Bull・Adversary・Judge が見るのは渡されたパッケージだけ
（情報分離・不変条件4）。
