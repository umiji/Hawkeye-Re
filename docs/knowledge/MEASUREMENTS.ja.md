## 実際に届く業種名は13種類しかなく、全部GICS11セクターに対応付けられた(2026-08-17実測)

**測る理由**: T-002(業界ETFとの比較材料を審理3役に渡す)には「会社の業種名 →
その業界を代表するETFの銘柄コード」という変換表が要る。業種名の提供元は
Finnhub(米国株の企業情報・ニュースを配る無料API)の `finnhubIndustry` という項目で、
これはGICS(世界共通の業種分類。11の大分類を持つ)より細かく、独自の語彙を使う。
T-002の停止条件は「どのGICSセクターにも当てはまらない業種名が多数見つかったら
User確認」だったので、**実際に何が届いているかを数える必要があった**。

**方法**: 過去の審理結果を貯めた台帳(SQLiteファイル
`var/legacy/hawkeye-20260806-preEW.db` の `recommendations` テーブル)に入っている
全19件の推奨レコードから、審理3役に渡した資料(`brief`)の `sector` 欄を取り出して
集計した。実行日 2026-08-17。本番台帳 `var/hawkeye.db` は現在0件のため使えない。

| Technology | 3 | Information Technology |
| Real Estate | 2 | Real Estate |
| Hotels, Restaurants & Leisure | 2 | Consumer Discretionary |
| Semiconductors | 1 | Information Technology |

**19件・13種類。空欄は0件で、13種類すべてGICSの11セクターに割り当てられた。**

  入れたが、実際の会社によっては逆が正しい。運用で実例が出たら見直す。

## 売上の柱は、決算行が記録される時点ではもう検証できている — 26/26件(2026-08-13実測)

**測る理由**: `docs/backlog/EARNINGS_QUALITY_AUDIT.ja.md` 検証3②(2026-08-04調査)は
「決算の3本柱のうち売上の実績側が55件中55件とも未検証」という構造欠陥を報告していた。
原因(実績値をXBRL/発表文から埋める本番コードが存在しない)はEW移行のタスク1・2で
削除済みだが、**削った後、実際に売上が検証できるようになったかを実データで測った記録が
無かった**。監査書自身が載せている「74%がBEATに変わる見込み」は、事前登録済み841行に
合成実績を当てた**シミュレーション**であって、実測ではない。

**方法**: 使い捨ての台帳(`HAWKEYE_VAR` を退避パスに向け、本番の `var/` には一切触れない)
に対し、実際のFinnhub・EarningsWhispers(EW、決算専門サイト)から
`hawkeye scout --days 7` を1回、実行した(2026-08-13、対象窓 2026-08-06〜2026-08-12)。
走査が計算した `EarningsQuality.revenue`(3本柱判定のうち売上の柱の判定オブジェクト)の
`.status` を、3本柱判定まで進んだ全候補について集計した。

```
決算イベント 1500件 → サプライズ選別 185件 → 決算専門サイトに問い合わせ 50件
  → 3本柱判定(詳細取得) 26件 → 入口ゲート通過 15件
```

| 売上の柱の判定 | 件数 |
| --- | --- |
| beat(上振れ・検証済み) | **26** |
| miss / inline / unverified / absent | 0 |

**26/26 = 100%が検証できた**(うち21件はEWを唯一の提供元とする `whispers` 読み、
残り5件はEWが答えられずカレンダーへ戻した `finnhub` 読み — こちらも実績・コンセンサス
とも同一提供元なので検証は成立している)。2026-08-04時点の 0/55(0%) から改善している。

**この26件は「決算専門サイトに問い合わせた50件」でも「選別を通った185件」でもない**。
3本柱判定は、暫定スコアで並べた候補を**入口ゲート通過15件に達するまで**歩いて enrichする
仕組み(`scout_target_gate_passed = 15`)なので、この26件は元々EPS・売上の両方が強く
上振れている名前に偏っている集団 — ただし審理に回る候補は必ずこの集団からしか
出ないので、測るべき母集団としては正しい。

**留保**:
- 単発の1週間窓(1標本)。同じ理由(過去日付への遡り取得手段が無い)で、独立した
  第2の窓を同じセッション内では取れなかった
- **26件全件がbeatで、miss/inlineが1件も出なかった**。これは「検証できるようになった」
  こと自体の確認としては十分だが、**「上振れ以外でも検証できるか」までは今回の標本では
  確認できていない**(スコアリングがEPS・売上の同時上振れを選好するため、標本が
  そちらに寄るのは仕組み上自然)
- 監査書の74%(753件中558件BEAT)とは母集団も測り方も違うため直接比較できない。
  シミュレーションが「データが揃うかどうか」だけを測ったのに対し、これは実際の
  3本柱判定の結果そのもの

## コンセンサスは決算の前後でほぼ動かない — 一致率88.9%(2026-08-11実測)

**標本**: 2026-08-09 20:50〜20:52(JST)に使い捨て台帳 `var/drift-experiment.db` へ
事前登録した383行。うち決算予定日が到来した173行を、2026-08-11 22:35(JST)に
`hawkeye consensus drift` で決算後の窓口と突き合わせました。

**方法**: 決算前に `/api/getstocksdata/` から取って保存した予想(`eps_avg` /
`revenue_avg`)と、決算後に `/api/epsdetails/` が返す同じ四半期の予想
(`estimate` / `revenueEstimate`)を比較。四半期ラベルが一致する行だけを数え、
EPSは半セント、売上は0.01%を「同じ数字」とみなす丸め幅としています。

```
比較できた 173 件 / 変わらなかった 136 件 / 動いた 37 件 (一致率 78.6%)
/ まだ決算が出ていない 159 件 / 別の四半期の決算が返ってきた 0 件
/ 比べる数字が無い 14 件 / サイトを読めず 37 件
```

**この78.6%をそのまま読んではいけません。** 記録が決算より前か後かで割ると、
まったく違う2つの母集団が混ざっていました。

| 記録のタイミング | 件数 | 変わらなかった | 動いた | 一致率 |
| --- | --- | --- | --- | --- |
| **決算より前に記録**(＝本来の事前登録) | 153 | 136 | 17 | **88.9%** |
| **決算より後に記録**(2〜9日後) | 20 | 0 | 20 | **0.0%** |

後者20件は次項の欠陥によるもので、事前登録の性能を表す数字ではありません。

**動いた17件のうち12件は、予想EPSの絶対値が0.15ドル未満**の銘柄です
(`RXT -0.09→-0.1`、`VFF 0.01→0.02` など)。率が大きく見えるのは分母が小さいためで、
EPSサプライズの信頼下限 `scout_min_abs_eps_estimate = 0.10` に近い水準の会社が
多く含まれます。

⚠️ **未解決**: 「動いた」がアナリストの予想改定なのか、2つの窓口がもともと違う数字を
持っているだけなのかは、この測定では切り分けられていません。

**【2026-08-13 決定】この未解決点を残したまま、事前登録を「毎日必ず回す運用」からは
外しました。** 切り分けを待たずに済んだ理由は、事前登録が必要だった別の・より強い
根拠(Yahoo Financeの予想取得エンドポイントが決算後に1四半期分ズレた数字を返す
バグ)が、無関係な変更で既に解消していたと分かったため。コード・記録は削除して
いないので、この17件の切り分け自体は今後もこの実測データを使ってできます。
判断の全体像は `docs/design/SET_H_G_DECISIONS.ja.md` を参照。

## EWの「値なし」番兵 999 は whisper 欄だけではない(2026-08-08)

**測る契機**: 「アナリスト人数の関門を、上限＝下限（レンジが開いていない）で
代用できないか」を検討するために fixture 47銘柄の上下限を数えたところ、
上限＝下限の6件のうち1件（ABTC）が **999.0/999.0/999.0** でした。

|---|---|
| `estimate`（EPSコンセンサス） | **8/47** (AATC・ABTC・ACFN・ACNT・ACTG・ADMA・AMBO・ANDE) |
| `highEstimate` / `lowEstimate` | 1/47 (ABTC) |
| `whisper` | 36/47 |
| `eps` / `revenue` / `revenueEstimate` | 0/47 |

→ **`estimate: 999.0` の8件は、上下限が欠けている8件と完全に一致します。**
つまり999は「コンセンサスを誰も出していない」の意味で、EPS予想が$999だった
わけではありません。

**見逃していた影響**: 999を数字として読むと、$0.30で着地した会社が

通さないのでどちらにせよ落ちますが、**落選記録には「会社が大きく未達だった」
と残ります** — 実際は「測る物差しが無かった」のに。不変条件6の、
気づきにくい方向の違反です。

**対処済み**: `estimate` / `highEstimate` / `lowEstimate` / `revenueEstimate`
も番兵を外すようにしました（`_NO_VALUE`）。結果、この8件は
`eps_consensus_missing` として正しく報告され、**決算まるごとFinnhubの数値に
フォールバック**します。

## EarningsWhispers のレート制限と利用条件(2026-08-07)

**測る理由**: 走査をEWに配線すると1回の実行で最大50リクエストを連続で出します。
絞られるかどうかを**配線前に**知らないと、本番で初めて分かることになります。

**方法**: fixture の先頭20銘柄に `/api/epsdetails/{ticker}` を**待ち時間なしで連続**
実行し、HTTPステータス・応答時間・絞り込み系ヘッダを記録。標本20件。

| 測定項目 | 結果 |
|---|---|
| HTTP 200 で返った | **20/20**。エラー0件 |
| 実効レート | **184回/分**(逐次・sleepなし。6.5秒で20件) |
| レート制限系ヘッダ(`RateLimit-*` / `Retry-After`) | **1件も返らない** |
| 応答時間 | 中央値 **0.31秒**、最小0.25秒、最大0.95秒(初回のみ接続確立分) |
| 後半で遅くなったか(絞りの兆候) | **なし**。前半平均0.36秒 → 後半平均0.29秒と**逆に速い** |

→ **N=50 の連続実行は、この標本では絞りに触れません。** 50件でも約16秒。
Yahooの62回/分より速く、走査の所要時間としても問題になりません。

**未測定**: 絞りが**どこで**始まるかは測っていません(上限を探る試験は先方への負荷が
本番と釣り合わないため実施せず)。分かったのは「50件の水準では起きない」ことだけです。

### HTTP 500 は「散発的」ではなく、銘柄ごとに決まっている(2026-08-08 訂正)

> ⚠️ **2026-08-07 に「散発的なサーバ側エラー」と書いたのは誤りでした。**
> 同じ銘柄で再現するか確かめずに「散発的」と結論していました。以下が訂正後の
> 測定です。

50件の連続実行を本番と同じ形で3回行った結果:

| 実行 | 成功 | HTTP 500 |
|---|---|---|
| 大型株50銘柄(単体スクリプト) | 49 | **1**(GOOG) |
| 本番の走査から50銘柄(ライブ・1回目) | 45 | **5** |
| 同・2回目(数十分後) | 47 | **3**(INOD・UMAC・GAIN) |

**同じ銘柄が毎回失敗します。** INOD・UMAC・GAIN を単独で2回ずつ叩くと、
**6回すべてが HTTP 500** で、返るのは**同一の96,272バイトのHTMLエラーページ**。
同じループの中で ADM は毎回JSONを返します。実効レートは177回/分のままで、
`Retry-After` も返りません。

→ **絞り込みでもなく、一時的な障害でもありません。その銘柄について
エンドポイントが常に失敗する**、という性質です。原因(レコード不在で
バックエンドが例外を投げている等)までは特定していません。

**含意（実装に反映済み）**:
- **5xx と接続エラーは別物として扱う。** 5xx は再試行1回で「その銘柄の性質」だと
  確定させ、**保留にはせずカレンダーの数字にフォールバック**する。保留にすると
  48時間ぶん毎回同じ拒否を買って打ち切るだけになる
- **接続エラー(何も返ってこない)は再試行2回・保留する。** 会社について何も
  分かっていない状態なので、待つ価値がある

### 利用条件(2026-08-07 時点の原文確認)

| 項目 | 内容 |
|---|---|
| `robots.txt` | `User-agent: *` に対し **`Disallow` が1行も無い**。`Crawl-delay` も無し |
| 利用規約(`/usage`) | 自動アクセス・スクレイピング・ボット・API利用・リクエスト頻度に**言及なし** |
| 唯一の関連条項 | **再配布の禁止** — 書面の同意なく "reproduce, retransmit, distribute, disseminate, sell, publish, broadcast or circulate" してはならない(非商用の紙のメモへの単発転載のみ例外) |

→ **本システムの使い方は再配布に当たりません**。取得した数値は手元の台帳
(`var/hawkeye.db`)と本人向けの日本語レポートにしか出ず、外部への公開・販売・
配信はありません。⚠️ **将来レポートを外部公開する機能を足すときは、この条項に
戻ってくること。**

## EarningsWhispers のサマリ文と実績の安定性(2026-08-06)

**方法**: 2026-08-05に採取したfixture 10銘柄を翌日(8/6)に引き直し、
`summary` 文字列と実績を突き合わせた。標本10件。

| 結果 | 件数 | 意味 |
|---|---|---|
| 同じ決算・サマリが**完全一致** | 5 (ACAD/ADM/AME/AMD/ALAB) | 確定した決算のサマリは**書き換えられない**。文中の「現在のコンセンサス」は発表直後の値のまま凍る |
| 同じ決算・サマリが**変化** | **1 (ADEA)** | **実績EPSが $0.34 → $0.42 に改訂された**(売上は不変)。下記 |
| 別の決算に入れ替わった | 4 (ACA/ADMA/ADNT/ALB) | 8/5採取時は前期のままだったが、**8/6には8/5発表分に更新されていた** |

### 1. サマリ内の「現在のコンセンサス」は使える

サマリはEWが発表直後(DUOLなら16:02 ET、リリースの数分後)に書き、以後
書き換えない。したがって文中の "The current consensus ... estimate is ... for the
quarter ending ..." は**アナリストがガイダンスに反応して修正する前の値**であり、
ガイダンスの物差しとして汚染されていない。**Yahooを翌四半期コンセンサスのために
残す必要は無い**(2026-08-06に一度そう提案したが、この測定で撤回)。

同じ47銘柄のfixtureでの出現率:

| 項目 | 件数 |
|---|---|
| サマリに「現在のコンセンサス」の記述がある | 25/47 |
| うち**翌四半期**の物差し(EPS 2・売上 10) | 12 |
| うち**通期**の物差し(EPS 2・売上 15) | 17 |
| ガイダンスを載せている銘柄 | 20 |
| **↑のうち翌四半期の物差しも同じサマリにある** | **11/20** |

売上の対(売上ガイダンス×売上コンセンサス)が主流で、EPSは少ない。通期の物差しが
17件あるので、いま `guidance_period_not_comparable` で捨てている通期ガイダンスも
期間を揃えて比較できる余地がある。

### 2. EWは実績を後から改訂することがある(新発見・要対処)

ADEAは同じ決算(2026-08-05発表、2026-Q2)のまま、**実績EPSだけが翌日に
$0.34 → $0.42 (+24%) に変わった**。売上は $96.12M で不変。標本10件中1件だが、
影響は大きい:

- 決算行は**追記のみで書き換えられない**設計なので、早く読んだ $0.34 を記録すると
  その行自体は直せない
  → **【2026-08-07 対応済み】** 改訂は「新しい行を有効（`active`）で追加し、古い行を
  無効（`superseded`）に落として残す」形で書けるようになった
  （`StockStore.revise_print`）。$0.34 の行が残るのは意図で、順位を付けた時点で
  どの値を見ていたかを消さないため。**ただし改訂を検出してユーザーに差分を見せる
  処理（タスク8.5）はまだ無い**ので、走査は改訂を拾わない
- サプライズ比が丸ごと変わる。$0.34 と $0.42 では上振れ・下振れが反転しうる
- **48時間の保留は「実績が届くまで待つ」規則であって「実績が動かなくなるまで
  待つ」規則ではない。** 届いた直後に読むほどこの改訂を踏みやすい

未測定: 改訂の発生率(標本10件では 1/6 = 17%だが、確定済み決算6件のうち1件という
極めて小さい標本)、改訂が起きる時間帯、改訂の向き。

### 3. 48時間の保留は足りている(暫定)

8/5採取時に前期のままだった4銘柄は、**4件とも翌日には当期に更新されていた**。
「EWの実績反映は約1日遅れ」(2026-08-05測定、16/16件)と整合する。48時間で
足りない事例はまだ観測されていない。ただしIPO直後銘柄(SPCX)は未測定。

## ガイダンス(会社が出す業績見通し)をコードでどこまで読めるか(2026-08-10)

**母集団**: 決算専門サイト EarningsWhispers の応答を記録した47銘柄
（`tests/fixtures/whispers/`・2026-08-05採取。**無作為標本ではない** — アルファベット順の
先頭付近に偏っています）。数えたのは「要約文（`summary`）の中で、会社自身が将来について
述べている文」です。

| 項目 | 修正前 | 修正後 |
| --- | --- | --- |
| 会社が将来について何か述べている | 25/47 | 25/47 |
| **コードが数字のレンジを読み取れた** | **20** | **23** |
| 文は見つけたが数字を取れなかった | 1 | 2 |
| **文そのものを認識できなかった** | **4** | **0** |

修正の中身は書き出しの言い回し2つ（`continues to expect` / 前置きを挟む
`said, ... , it now expects`）を足しただけです。ADEA・ADV・AHCO・ALB の4件は、
通期の売上レンジを普通の数字で書いているのに「ガイダンス開示なし」として記録されて
いました。

**残る2件は、LLMに読ませても読めません。** 文中に比較可能な数字が存在しないためです:

- **ADV**: `2026 revenue of $3.54 billion to $2.67 billion` — 上限が下限より小さい。
  提供元の打ち間違い。中央値を取ると $3.10 billion という誰も公表していない数字が出る
  → `range_inverted` として拒否
- **ALGT**: `third quarter results to range from a loss of $1.00 per share to breakeven`
  と `2026 earnings of more than $6.00 per share` — 一方は非数値、もう一方は上限が無い

**⚠️ この表から「LLMに読ませても0件」と結論したのは誤りでした（2026-08-10 訂正）。**
残る2件は、どちらもLLMなら読めます:

- **ADV** `$3.54 billion to $2.67 billion` — 打ち間違いではなく、**上限を先に書いた
  だけ**。順序が入れ替わっただけの範囲で、コード側でそれを打ち間違いと判別する手段は
  ありません（「打ち間違い」という読みは私の憶測でした）
- **ALGT** `a loss of $1.00 per share to breakeven` — **-1.00〜0.00**。
  言葉の意味が分かる読み手なら普通に読めます

さらに本質的な点として、**この表の「読めた23件」という数字自体が誤解を招きます**。
パターンが読めるのは、パターンを書いたときに見た形の文だけです。標本を増やせば
「読めた件数」は増え続け、同時に「読めない形」も出続けます。件数で測る限り
成功に見え続ける、という性質があります。

→ **2026-08-10以降、ガイダンスはエージェント（AI）が全部読みます**
（`hawkeye/scout/guidance_agent.py`）。コード側の読み取りは関数ごと削除しました。
**アナリスト予想の文は今もコードで読みます** — 提供元が数値から機械生成している文
なので形が1つしか無く、パターンが正しく効く唯一のケースだからです。
