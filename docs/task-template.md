# タスク定義テンプレート

`docs/task-list-hawkeye-re.csv`（一覧）と`docs/tasks/T-XXX.md`（個別詳細
ファイル）に正式登録する前に、この8項目で仕様を確定させる。埋まっていない
項目があるまま実装を始めない — 空欄は「省略可」ではなく「未確認」を意味
する。運用手順（このテンプレートをいつ・どう使うか、CSVと個別ファイルへの
書き分け方）は`hawkeye-task-cycle` Skill
（`.claude/skills/hawkeye-task-cycle/SKILL.md`）と`docs/tasks/README.md`
を参照。

## 記入項目

1. **タスクID / タスク名**
   ID は`docs/tasks/README.md`のID採番ルール（`T-###`、3桁連番、再利用
   禁止）に従う。タスク名は**10〜40文字程度**で、そのタスクを端的に
   説明したものにする。ID・タスク名はどちらも`docs/task-list-hawkeye-re.csv`
   の列に入り、個別ファイル`docs/tasks/T-XXX.md`のタイトル（`# T-XXX: タスク名`）
   にも使う。詳しい経緯や理由はここに書かず、項目2〜4（個別ファイルの
   「## 目的」「## 変更範囲」「## 禁止事項」）に書く。

2. **目的（なぜ変更するのか）**
   何のためにこの変更が必要か。「〜を直す」だけでなく、放置した場合に何が
   困るかを書く。

3. **変更範囲（触るファイル・機能）**
   触る予定のファイル/機能を列挙する。ここに無いファイルへの変更が必要に
   なった場合は、別タスクとして切り出すか着手前にユーザーへ確認する。

4. **禁止事項（触ってはいけない箇所・推測実装の禁止）**
   この変更で絶対に触ってはいけない箇所を明記する。仕様が不明な点を推測で
   埋めることも常に禁止（`CLAUDE.md` の共通禁止事項）だが、このタスク固有の
   追加禁止事項があればここに書く。

5. **完了条件（Yes/Noで判定可能な具体的基準）**
   「動作確認した」のような曖昧な基準ではなく、実行するコマンドと期待する
   出力で書く（例:「`pytest tests/test_x.py` が全件成功する」）。

   **必須: Userまたは運用手順書が実際に実行するコマンドと、その期待出力を
   最低1つ含めること。** 関数を直接呼ぶテストだけで完了条件を構成しては
   ならない — テストが全件緑でも、それはロジックの証拠であって、Userが
   実際に通る経路が直った証拠ではない（実例 2026-08-17 T-005: 完了条件
   4つ全部が内部関数を直接呼ぶテストで、手順書が使う
   `hawkeye case open --from-earnings` を一度も実行しないまま進捗100%に
   到達し、運用経路は壊れたままだった）。そのコマンドが実環境でしか実行
   できない場合は、その旨と「誰が・いつ実行して確認するか」を完了条件に
   明記する。

6. **テスト方法（単体/結合/回帰/実環境確認の切り分け）**
   どの種別のテストで何を検証するかを分けて書く。実環境確認が必要かどうか、
   必要なら誰がいつ行うかも明記する。

7. **停止条件（仕様矛盾、破壊的変更、想定外差分の検知時）**
   このタスク固有の停止条件があれば書く。無ければ「`CLAUDE.md` の共通停止
   条件のみ」と明記する。

8. **依存関係（先に完了しているべきタスクID、無ければ「無し」）**
   他タスクの完了に依存する場合はタスクIDを書く。書式は2種類:
   - `T-001（ブロッカー）`: 着手前にT-001が`完了`していないと進められない。
   - `T-001（推奨: 理由）`: 必須ではないが、着手順序として先に行うことを
     推奨する場合。理由も書く。
   依存が無い場合は「無し」と明記する。`-`や空欄のままにしない — それは
   「未確認」を意味してしまう（項目4と同じ、推測で埋めない考え方）。
   `docs/task-list-hawkeye-re.csv`の「依存タスク」列には短縮形（例:
   `T-001（推奨）`）を書き、理由の全文は個別ファイル
   `docs/tasks/T-XXX.md`のメタデータ欄「依存」に書く。
