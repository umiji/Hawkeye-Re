## 前提（崩すとテーブル設計が巻き戻る）

**3役の結論は決算行に書き戻らない。** 審理で分かったことは案件ファイルと台帳の
ジャーナルに残る。この前提がある限り、審理側で何を読ませるか（資料収集ステップの中身
など）を後から決めても、ここで作るテーブルには影響しない — 資料束用のテーブルが1つ
増えるだけで、既存テーブルの形は変わらない。

⚠️ もし将来「10-Kを読んだ結果で実績値を上書きする」となると、`earnings_prints.source`
に「データ提供元ではない値」が要り、審理の結論が決算行に書き込まれることになり、
**順位を付けた時点で何を知っていたかが壊れる**（事前登録の意味が消える）。
**`source` に入るのは常にデータ提供元の名前だけ**にする。

> **実装時の補足（2026-08-07）**: 現在の値は `finnhub` と `yahoo` の2つです。
> EW配線（タスク4）前の今は、順位付け前にEPSを取り直す第2ソースがYahooだからです。
> 全部 `finnhub` にすると「第2ソースで確認済み」という事実が失われます。
> タスク4の完了時に `yahoo` が消えて `whispers` に置き換わり、`finnhub` /
> `whispers` の2値になります。**守るべきはこの2値であること自体ではなく、
> 「値は必ずデータ提供元であって、審理の結論ではない」という制約**です。

### 審理側と決算行の実際の関係（2026-08-07 確認）

- **読む**: `case open` が決算行とコンセンサスを引いて、審理に渡す触媒テキストと
  構造化ファクトを組み立てる
- **書く**: `case open --from-earnings`（走査を経ず単一銘柄を審理にかける経路）は
  決算値を取得し直して**決算行を書く**（`judge_ticker` → `_record_print`）。走査と同じ
  「決算を記録する」処理なので問題ない
- **3役自身はDBを引かない。** 渡されたパッケージだけを見る（不変条件4）

**この関係から出る実装制約2つ**

1. **論理削除フラグを読み取り側が尊重すること。** 実績改訂で古い行を `superseded` に
   落としたとき、`case open` の読み取りが必ず `active` の行を拾わないと、審理が
   古い値で始まる（タスク5・8.5に直結）
2. **物理削除は案件が参照している決算行を守ること。** 推奨内容そのものは書き換え不能に
   固定されるので案件は壊れないが、「この判断はどの決算行を見たのか」の辿り直しが
   できなくなる（タスク8.5の物理削除コマンドの制約）

  表現として十分**で、1行の中にJSON配列を溜めるより監査しやすい
- **打ち切り（`stage="actual_timeout"`）はもともと落選記録に書く計画だった。**
  終わった状態を落選記録に、途中の状態を別テーブルに置くのは一貫しない。同じ決算の
  履歴が2つのテーブルに割れる
- 統合すると1つの決算の一生が時系列で並ぶ:
  ```
  scan 12  ADM 2026-08-04  actual_pending   前期のレコードが返った
  scan 13  ADM 2026-08-04  actual_pending   前期のレコードが返った
  scan 14  ADM 2026-08-04  ranking_cutoff   実績到着、順位7位
  ```
- 試行回数 = `actual_pending` 行の件数 / 各回の理由 = 各行の payload

**⚠️ 48時間の起点をEWの応答から取ってはいけない。** 保留中はEWが**前期のレコード**を
返している状態なので、その応答の発表時刻は前四半期のもの。48時間はとっくに過ぎている
ことになる。起点は**Finnhubカレンダーの決算予定日**から取る（走査のたび同じ値なので
行が増えても起点がずれない）。

**⚠️ 重複除去が保留中の決算を除いてはいけない。** `screened_candidates` が重複除去の
判定元なので、保留行を書くとそこで弾かれて二度と読まれなくなる。「保留中は除外しない」
という例外が要る（別テーブルでも同じ例外が必要なので、統合による増分ではない）。

**ドロップ候補レビューの扱い**: `actual_pending` は**評価していない**名前なので統計から
除外する。`actual_timeout` は「データが来なくて落とした」という実測なので**含める**。

**保留になる条件**
- **A-2**: EWが前期のレコードを返す（まだ今回の決算を取り込んでいない）
  → 検出は `q1Ref` と、カレンダー上の決算予定日から期待される四半期の突き合わせ。
  **`status` フィールドは使えない**（前期にも当期にも同じ `status: "No"` が付く実測あり）
- **A-5**: EWが応答しない（HTTP失敗）→ **保留の試行回数に数えない**
  （接続についての事実であって会社についての事実ではない）

**48時間は打ち切り期限であって待ち時間ではない。** 期限内は `run` を実行するたび
**毎回**読み直す。期限を過ぎたら打ち切り、落選記録に `stage="actual_timeout"` を残す。

**保留中は決算行を書かない**（タスク5の一意制約と直結）。

</details>

### 6.7. 構造的に落ちた会社を、走査の入口で丸ごと飛ばす（2026-08-08 追加・User指摘）

**いまの実装は中途半端です。** 過去に入口ゲートの構造3条件（株価・時価総額・

その先は普通に処理しています。

| 処理 | いまの挙動 |
| --- | --- |
| カレンダーに載る | 載る |
| サプライズの足切り | 通れば通る |
| **EWへの問い合わせ** | **省く（ここだけ）** |
| 順位付け | する |
| **株価・時価総額の取得**（1銘柄2回のAPI呼び出し） | **する** |

**⚠️ 「事前登録の側では効いている」は誤りでした（2026-08-08 訂正）**

セッション中に「走査では元が取れないが事前登録では効いている」と説明しましたが、
**間違いです。同じ有効期限の問題が事前登録にも当たります。**

書く側と読む側を整理すると:

| | 誰が | 対象 |
| --- | --- | --- |
| **銘柄マスタの行を作る** | 主に事前登録 | 2営業日以内に決算予定の全銘柄（実測855件） |
| **構造判定を書く** | **走査だけ**（入口ゲートの直後） | 入口ゲートに到達した銘柄のみ（1走査で最大45件） |
| **構造判定を読む** | 事前登録 ＋ 走査（2026-08-08 追加） | 上記 |

事前登録は**行は作るが判定は書きません**。マスタ870行あって判定が2件しかなかったのは
これが理由です。

そして事前登録も、同じ会社に次に問い合わせるのは**約91日後**（決算は四半期ごと）
なので、**90日の有効期限を超えます**。走査より再訪頻度は高い（上振れの有無に関係なく
毎四半期見る）ものの、**期限切れの問題は同じように起きます**。

→ したがって下記の代案（会計四半期で判別する）は、**走査と事前登録の両方に必要**です。

**⚠️ 有効期限 `stock_triage_ttl_days = 90` も設計として筋が悪い**

- コメントは「およそ2決算期」と書いているが、**90日は約1決算期**
- 決算間隔は91〜92日なので、判定は**次の決算が来る直前に失効する**
- 日数という物差し自体が、決算という四半期の出来事に合っていない

**代案（Userの提案。こちらの方が筋が良い）**: 日数ではなく**会計四半期**で判定する。

- 銘柄マスタに**最後に審査した会計四半期**を持たせる
  （⚠️ **`Stock.last_reviewed_fiscal_quarter` は既に存在します** — 新設不要）
- 次の走査で同じ銘柄が出たとき、**その決算の四半期ラベルが
  「記録済みの四半期」と同じか、その次か**で判別する
- 同じ四半期 → 既に見た決算なので飛ばす
- 次の四半期 → 新しい決算なので、構造判定を**もう一度取り直す**
  （株価$3の会社が$9になっている可能性があるため）

これなら「90日」という決算暦と無関係な数字が要らなくなり、

### 10. 過去決算の遡り取得 — ✅ **完了（2026-08-10）。ただし4四半期・EPSのみ**

> **8四半期は達成不能でした。** 実際に叩いて確認した結果、銘柄別の履歴は
> **4行が上限で、売上の欄が無い**（`docs/knowledge/MEASUREMENTS.ja.md`「過去決算は
> 4四半期しか遡れない」）。下の「必要な理由」1番（4連続と8四半期ぶりの区別）は
> **この経路では満たせません**。レポートにその旨を毎回明記しています。
>
> 実装: `hawkeye/scout/backfill.py`（取得と記録）、
> `FinnhubProvider.earnings_history`（1銘柄1リクエスト）、
> `render_backfill_ja`（走査レポートへの表示）、
> `scout_backfill_quarters = 4` / `scout_backfill_top_n = 3`。
> 上位3銘柄だけを対象に、順位確定後に叩きます。
> **既に記録のある四半期は上書きしません**（既存行は売上と確定コンセンサスを
> 持っており、EPSだけの行で置き換えるのは更新に見える劣化）。

**当時の状況: 遡り取得の機能はどこにも無い。** 新しく候補になった銘柄の過去4〜8四半期は空。
今あるのは「今回の窓に入っている決算のうち、候補にならなかったがマスタに載っている
銘柄の分も記録しておく」処理だけで、遡りはしない。

**必要な理由（私の判断）**
1. 4四半期連続で上振れている会社と8四半期ぶりに1回上振れた会社では、次の四半期への
   含意がまったく違う
2. **反論役（Adversary）の武器が減る。** 「今回は良かったが過去2四半期は下振れていて、
   今回だけ一過性の会計要因では」という攻撃ができない。反論役の材料が薄いと審理が形骸化する
3. 論旨精度の採点で「元々振れ幅が大きい銘柄」といった評価ができない

**取得手段**: 現在Finnhubから使っているのは日付範囲のカレンダーだけで、**銘柄別の決算
履歴を引く経路は未実装**。Finnhub側には銘柄別の決算サプライズ履歴のエンドポイントが
あるはずなので、3枠に絞ってから叩けば1銘柄1リクエストで安く済む。

### セッション方式の情報分離を、指示から機構に変える

**現状の正確な姿（2026-08-07 確認）**

| | セッション方式 | API方式 |
| --- | --- | --- |
| **文脈の分離** | **技術的に保証されている** — 役ごとに新しいサブエージェントが立ち上がり、会話履歴を引き継がない。Bullの出力がAdversaryの文脈に入ることはあり得ない | 保証 |
| **ファイルの分離** | **指示のみ** | そもそもファイルが無い |

サブエージェントはReadツールを持っている（3ファイル読んで1つ書く必要があるため）。
スキルの「他のファイルを読むな」は**指示であって制約ではない**。同じディレクトリに
他の役のファイルがあれば機構的には読める。

⚠️ CLAUDE.md の記述「セッション方式の情報分離は運用上の規律であって機構ではない」は、
**文脈の分離については不正確**。文脈は構造で分離されている。規律に頼っているのは
ファイルアクセスの1点だけ。

**閉じる方法**
- サブエージェントに**ファイルのパスではなく中身を直接渡す**（入力3点をプロンプトに埋め込む）
- **ファイルツールを持たない専用のエージェント型**を定義する
- 出力はJSONを最終応答として返させ、指揮役がそのままファイルに落とす
  （「役の出力を編集しない」規律は今と同じ）

これでAPI方式と同じ保証になる。実装は軽い。
