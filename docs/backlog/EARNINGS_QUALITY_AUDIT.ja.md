# 検証1：データセットは正しく取得できる状態か → **否。3本柱すべてに欠落があり、うち2つは構造的**

## EPS

| 項目 | 実測 |
|---|---|
| 実績（Finnhub決算カレンダー） | 55/55 = 100% |
| 実績（Yahoo再取得） | 21/55 = 38% |
| コンセンサス・事前登録 Yahoo | 702/841 = 83.5% |
| コンセンサス・事前登録 Finnhub | 760/841 = 90.4% |
| うちアナリスト3人以上 | 518/841 = **61.6%** |

**発見した異常**：決算数値をYahooで再取得し直す照合処理（`hawkeye/scout/verify.py` の
`verify_events`）の成功率が、8/3の走査では16件中16件（100%）だったのに、
**8/4の走査では40件中6件（15%）まで落ちている**（未確認34件）。取得件数の上限には
達していない（`verify_budget_exhausted: false`）。

この数字は走査レポートに「数値の照合: 40件を Yahoo で再取得 → 確認 6件 / 未確認 34件」
と表示されており、隠されてはいない。ただし**成功率が落ちても走査は止まらず、異常としての
警告も出ない**。原因（yfinance側の一時的な不調か、恒常的な仕様変更か）は未特定。

## 売上

| 項目 | 実測 |
|---|---|
| 実績（Finnhub） | 55/55 = 100% |
| 実績（EDGAR XBRL / 発表文） | **0/55 — 本番コードから一度も書かれていない** |
| コンセンサス・事前登録 Yahoo | 803/841 = 95.5%（ただし**117件が 0.0**） |
| コンセンサス・事後再構成 Yahoo | **0/55 = 0%** |

問題は2つ。

1. 決算内容の器（`EarningsPrint`）には売上実績の欄が3つ（Finnhub / XBRL / 発表文）あるが、
   **XBRLと発表文の欄に値を書き込む本番コードが存在しない**。この2フィールドを設定している
   のはテストと `scripts/dry_run_earnings_quality.py` だけ。決算発表文を取り込む処理
   （`hawkeye/scout/release.py` の `apply_release`）もEPSとガイダンスは書くが売上は書かない。
   → **売上実績は構造的に永久に単一ソース**。
2. 決算発表**後**にYahooから取れるコンセンサスには、その四半期の売上予想が含まれない
   （`hawkeye/marketdata/consensus.py` の `shift_after_print` の設計通り、発表後の
   「今四半期」は既に次の四半期を指すため）。→ 事後再構成では売上コンセンサスが0%。

## ガイダンス

**0/55。取得経路が実質的に閉じている。これが検証1で見つかった最大の構造欠陥。**

ガイダンス（会社が自ら示す次期の業績見通し）が入る唯一の入口は、人またはエージェントが
会社の発表文を読んで `var/releases/` に置いたJSONを取り込む処理（`apply_release`）。
ところが、その取り込みを起動するかどうかを決める判定
（`hawkeye/scout/release.py` の `needs_release_read`）は、条件がこの1行だけ：

```python
return "actual_disputed" in quality.eps.flags   # release.py:74
```

つまり **「EPSの実績値が2つのデータ提供元で食い違っているとき」だけ**発表文を要求する。
ガイダンスが欲しいかどうかは条件に一切入っていない。結果、発表文の読み取り依頼を記録する
テーブル（`release_requests`）は**0行**、ガイダンスも0件。

比較の物差し側（翌四半期コンセンサス）は事前登録で83.6%（EPS）／95.5%（売上）取れている。
**足りないのは比較相手を取りに行く仕組みだけ**という見立ては正しいが、原因は
「運用されていない」ではなく「**別目的の条件に相乗りしていて起動しない**」。

# 検証3：評価方法は妥当か → **不当な不利が3件、不当な有利が1件**

## ① 【虚偽・最優先】ガイダンス欠損を「会社が開示していない」と断定している

審理に実際に渡された文面を7件すべて確認した。3本柱判定が動いた4件
（LIND/CNH/BLZE/AMZN）は全件、以下がそのまま入っている：

```
Guidance not disclosed — consensus [guidance_not_published]
```

一方、3役に共通で渡される指示文（`hawkeye/tribunal/prompts.py` の `_SHARED_DOCTRINE`）
にはこう書かれている：

> A null value on these fields means unverified/unavailable, NOT "no activity" or
> "zero surprise" — **never treat a missing field as evidence of anything.**

**指示文が「欠損を証拠にするな」と言っている横で、カタリスト説明文が「開示なし」という
事実を主張して指示を上書きしている。** LINDは実際にはFY2026売上ガイダンスを
$800-850M → $830-860M に引き上げており、この主張は事実に反する。

## ② 【不当な不利】売上の柱が55/55件で未検証

原因は会社ではなく我々のデータ欠落（検証1の売上の項）。影響は2つ：順位付けで最大20点を
取り逃がす（満点は概ね85点）、そして審理文に "must not be argued as a beat"
（上振れとして主張してはならない）と明記される。**強気側は使えず、反論側は攻撃できる**
という非対称。

**ただしこれは事前登録で解消に向かう見込み。** 事前登録済み841件に
「両コンセンサスを10%上回る合成実績」を当て、データの揃い具合だけで判定させた結果：

| | 現状（事後再構成55件） | 事前登録シミュレーション（753件） |
|---|---|---|
| 売上 BEAT | 0 (0%) | 558 (74%) |
| 売上 未検証 | 55 (100%) | 179 (24%) |
| 判定「良い決算」 | 0 (0%) | 328 (44%) |

**留保**：これは合成実績による「データが揃うか」の測定であり、実際に良い決算が増えると
いう意味ではない。

## ③ 【要検討】コンセンサスが1ソースなら未検証、実績が1ソースなら通る

柱を未検証に落とすフラグ（`_BLOCKING_FLAGS`）に `single_source_consensus` は入っているが、
`single_source_actual` は入っていない。

これは、実績値の食い違いをブロック対象から外したとき（`config.py` の
`earnings_actual_dispute_blocks`）に書かれた理由と同じ論点 —
「1ソースの実績は受け入れるのに、2ソースが食い違うと拒否するのでは、情報が多い方が
不利になる」。同じ検討がコンセンサス側には適用されていない。妥当性は判断が要る論点。

## ④ 【不当な有利・新規発見】売上コンセンサスが 0.0 のとき、2ソース確認が黙って1ソースに落ちる

`0.0` は「値が無い」（None）ではないので、**「ソースが1つだけ」という警告フラグが立たない。**
一方、ゼロ除算を避けるため読み取り結果（`_pct`）は None になる。結果、**Finnhub1本の読み
だけでBEATが成立し、記録には「2ソース比較した」（`sources=2`）と残る。**

合成データで再現：

```
Yahoo売上コンセンサス 0.0（アナリスト18人）/ Finnhub 1.0e9 / 実績 1.05e9
  → 売上の柱: beat / sources: 2 / yahoo読み: None / finnhub読み: +5.0%
  → 四半期判定: good_quarter
```

該当形の事前登録行は現在 **売上18件・EPS1件**（アナリスト人数が下限を超えていて
`thin_coverage` にも引っかからないもの）。残り99件はアナリスト0人のため別の理由で
未検証に落ち、たまたま被害が出ていない。

これは `quality.py` 自身が冒頭で掲げる規則
「**a beat counts only when BOTH of them say so**」の違反であり、
**この系で唯一「甘い方向」に外れている箇所**。

# 調査方法（再現手順）

すべて `var/hawkeye.db` の読み取り専用オープンと、`assess_earnings` への再投入で測定した。
使用したスクリプトはスクラッチパッド限りで、リポジトリには含めていない。測定内容は：

1. `consensus_snapshots` / `earnings_prints` のフィールド充足率を kind 別に集計
2. 記録済み55件の決算を、紐づいたコンセンサス行と一緒に `assess_earnings` へ再投入し、
   柱の判定・フラグ・四半期判定を集計
3. 事前登録841行に「両コンセンサスを10%上回る合成実績」を当てて再投入（データ完全性のみの測定）
4. `var/cases/*.json` から、審理に実際に渡ったカタリスト説明文を直接読み出し
5. 0.0 コンセンサスの挙動を合成行で再現
