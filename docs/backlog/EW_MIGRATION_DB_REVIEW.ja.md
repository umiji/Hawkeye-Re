## 1. 数値の欄がベンダー名で固定されている（CRITICAL）

### 何が起きるか

決算内容の器（`EarningsPrint`）とコンセンサスの器（`ConsensusSnapshot`）は、
数値の欄そのものが `_yahoo` / `_finnhub` というベンダー名になっている。

```
EarningsPrint      : eps_yahoo, eps_finnhub(list), revenue_finnhub
ConsensusSnapshot  : eps_avg(=Yahooの分布), eps_finnhub, revenue_avg, revenue_finnhub
```

EWの数値をこのどちらかに入れると、**そのままの名前で外に出る**。しかも出口は
台帳だけではない:

- 日本語レポート（`hawkeye/reports/quality_ja.py:171-172`）に
  「Yahoo EPS=… / Finnhub EPS=…」と印字される
- **審理が読む英語のブリーフ**（`hawkeye/scout/quality.py:391-394`）にも
  `Yahoo +3.2%, Finnhub +2.9%` と書かれる

3つ目が特に重い。Bull（強気側の主張だけを作る役）と Adversary（書かれた論旨だけを
見て反論する役）は、この文章を事実として読む。EWの1つの数字を「2つのベンダーが
独立に確認した」かのように提示することになり、**対審の前提そのものを偽る**。
今回直したガイダンスの偽装（期間の違う数字を並べて+347.9%の上振れに見せていた）と
同じ種類の欠陥で、影響範囲はこちらのほうが広い。

さらに判定結果の器（`LegVerdict`）も `yahoo_surprise_pct` / `finnhub_surprise_pct`
とベンダー名固定。実績を解決する処理（`_resolve_actual(yahoo, finnhub, settled)`）も
引数が2ベンダー名で、**「2つのベンダーが一致して初めて上振れ」という骨格そのものが
Yahoo×Finnhubを前提に組まれている**。EW一本足ではこの骨格が成立しない。

### 選択肢

**案A: EW専用の欄を追加する（最小変更）**
- `eps_whispers` / `revenue_whispers` / `whisper_number` / `vendor_*` を足す
- 比較の骨格（`_resolve_actual` の yahoo/finnhub 引数）はそのまま、EWの値を
  「settled でも yahoo でも finnhub でもない第3の候補」として渡す
- 利点: 変更が小さい。既存テストの大半が生きる
- 欠点: **ベンダーが増えるたびに欄が増える**。判定結果の器とレポートと英語ブリーフに
  「Whispers」を足す作業が3か所に散る。骨格の嘘（2ソース前提）は残ったまま

**案B: 役割ベースに改名し、出所をラベルとして持つ（推奨）**
- 数値の欄を「何番目の観測か」で持ち、出所は文字列で添える

  ```
  EarningsPrint     : eps_readings: list[SourcedNumber]   # (source, value)
                      revenue_readings: list[SourcedNumber]
  ConsensusSnapshot  : eps_consensus / eps_range / eps_analysts / eps_source
  LegVerdict         : readings: tuple[SourcedPct, ...]
  ```
- `_resolve_actual` は「候補のリスト＋発表文の確定値」を受ける形に一般化
- レポートと英語ブリーフは出所ラベルをそのまま印字するので、**ベンダーが増えても
  文言の修正が要らない**
- 利点: 出所の偽装が構造的に起きなくなる。EW一本足でも将来2ソースに戻しても同じ器
- 欠点: `quality.py` の判定部を書き換える。テストの書き換えが広い（推定30〜50件）

**案C: いま何もせず、scout配線を先にやる**
- 却下。出所を偽った数字が台帳と審理に入る。前セッションで「配線の前に出所カラムを
  直す」と決めた理由がこれ

**私の推奨は案B。** 理由は3つ:
1. DBが空である今しか、改名の移行コストがゼロにならない
2. 案Aは器の嘘（2ソース前提）を残すので、EWの1つの数字を2ソース比較の枠に
   流し込む不自然さが判定ロジックの中に残り続ける
3. 「コードが規約を機械的に強制する」（不変条件3）の観点で、出所ラベルが
   数値と一体で運ばれる構造のほうが、後から嘘が入りにくい

ただし案Bはテストの書き換えが広く、1セッションで終わらない可能性がある。
**「案Bで進めるが、判定ロジックの一般化は段階を分ける」** のが現実的だと考えている。

## 2. 四半期ラベルの二重化（CRITICAL）

### 何が起きるか

「この決算はどの四半期のものか」というラベル（`fiscal_quarter`）の決め方が2通りある。

- **事前登録の側**（`hawkeye/scout/prereg.py:116-129`）: Finnhubカレンダーの
  `year`/`quarter` を使い、無ければ**発表日のカレンダー四半期**にフォールバック
- **EWの側**（`hawkeye/marketdata/whispers.py:145-160`）: 会社自身の年度末から
  逆算（NVDAの4月末締めは 2027-Q1）

このラベルは飾りではない。以下が全部ラベルの一致で動いている:

- コンセンサスの引き当て（`consensus_in_force(stock_id, fiscal_quarter)`）
- 同じ四半期を二度審査しない仕組み（`already_reviewed()`）
- 決算行の一意インデックス `(stock_id, fiscal_quarter, depth)`

ラベルがずれると、**インデックスは衝突しないので重複が防げず**、同じ決算が2行入り、
実績の行から見て事前登録のコンセンサスが引けなくなる（＝せっかく事前登録した
予想が使われず、事後再構成の弱い証拠に落ちる）。

### 測定した数字

**フォールバック（発表日のカレンダー四半期）は、ほぼ常に1四半期先を指す。**
6月末締めの四半期は7〜8月に発表されるので、発表日で四半期を数えると Q3 になる。

- EW実応答47銘柄: EWのラベルと発表日ベースのフォールバックが**41件中40件で不一致**
  （例: ADM は EW=2026-Q2 / フォールバック=2026-Q3）
- 退避した本番DB: 決算行55件中52件、コンセンサス896件中849件は
  **ソース自身のラベル**を使っている（＝Finnhubは通常 year/quarter を返す）。
  裏を返すと**約5%はフォールバックに落ちており、その分は1四半期ずれている**

つまりこれはEW移行で新しく生まれた欠陥ではなく、**既にあった潜在的な取り違えが、
EW移行で表面化する**という関係にある。EWは正しいラベルを返すので、フォールバックに
落ちた行とEWの行が別四半期として並ぶ。

### 対策案

- 「決算日からラベルを決める」フォールバックを**発表日ではなく四半期末**から
  決めるよう直す（EWは `quarter_end` を返すので、EWがあれば常に正しく決まる）
- ラベルの決定を1か所（`contracts/stocks.py`）に集約し、EWのラベルを唯一の正とする
- EWにもFinnhubにもラベルの根拠が無い場合は、**ラベルを付けずに保留**にする
  （推測したラベルで書き込むと、後から取り違えを検出できない）

これは案B/案Aいずれを選んでも必要な修正で、**出所カラムより先に直すべき**かもしれない。

## 3. `verified` の意味が失われ、深さの階段が1段に潰れる（HIGH）

決算行には「どこまで踏み込んで見たか」という深さ（`PrintDepth`）がある:

```
calendar_only → verified → xbrl_validated → release_read
```

`verified` の定義は「2ソースの実績を突き合わせた」。EW一本足では突き合わせが
起きないので、判定（`hawkeye/scout/quality.py:428`）の
`verified = event.eps_source == "yahoo"` は常に偽になり、**全部の行が
`calendar_only` に落ちる**。

これは表示上の問題では済まない。深さは**追記の鍵**で、同じ四半期を深めるときは
「より深い行を追記する」設計になっている（`hawkeye/scout/scout.py:266-278`）。
深さが1段しか無いと、

- 1日目: 実績がまだ来ていない状態の行が `calendar_only` で入る
- 2日目: 48時間の保留が明けて実績が届く。しかしこれも `calendar_only`
- → 既存行と同じ深さなので**黙って書き込みが捨てられ、実績が永久に記録されない**

今は「実績が無い決算行は書かない」ガード（`_record_cheap_history` が
`eps_actual is None` を飛ばす）があるので発火していないが、**保留の仕組みを
scoutに配線する段階で、これは確実に踏む**。

### 対策案

- `verified` の定義を「EWの当期レコードで実績が確認できた」に変える
  （2ソース照合ではなく、**当期の実績が実在することの確認**）。
  空DBなので旧定義の行と混ざらない
- 保留中の決算行は**書かない**ことを仕様としてテストに固定する
  （器を先に作ると上記の取りこぼしが起きる）

## 4. IPO直後の銘柄がEWに載らない（HIGH・ユーザー報告）

SPCX のようなIPO直後の銘柄はEWの反映が遅い。EWに記録が無い場合の戻り値は
「記録なし」（HTTP 204）で、保留の判定（`hawkeye/scout/waiting.py:75-76`）では
`no_record` になる。48時間で打ち切られる。

Finnhub / Yahoo には数値がある可能性が高い以上、**EW一本足はIPO直後の銘柄を
構造的に落とし続ける**。カタリスト駆動でサプライズを取りに行く戦略にとって、
上場直後の初決算は反応が最も大きい局面のひとつなので、これは意図しない盲点になる。

### 要測定（実装より先）

- SPCXのようなIPO直後銘柄が、発表から48時間以内にEWに載るか
- 載らないなら、`no_record` が続く銘柄だけ Finnhub の実績にフォールバックするか、
  それとも「EWに無い銘柄は対象外」と明示的に決めるか

**どちらを選ぶかは投資方針の判断なので、ユーザーに決めてもらう項目。**
なお `no_record`（EWがこの会社を知らない）と `previous_quarter`（EWは知っているが
まだ前期のまま）は既に区別して記録されるので、実データが溜まれば測定はできる。

## 5. 保留→打ち切りの銘柄が、ドロップ候補レビューから漏れる（HIGH）

落選記録（`screened_candidates`）は、サプライズ判定を通った銘柄が
その後どこで落ちたかを記録する表で、ドロップ候補レビュー（落選した銘柄を
一定期間後に測り直し、篩が間違っていなかったか検証する仕組み）はこの表を見る。

保留中の銘柄は**実績が無いのでサプライズが計算できず、そもそもこの表に入らない**。
48時間で打ち切られた銘柄は `earnings_actual_waits` に理由つきで残るだけで、
落選記録には現れない。

結果、**「データが来なかったせいで見送った銘柄」がレビューの視界から消える**。
これは検証プロトコル上の穴で、しかも一番知りたい種類の取りこぼし
（＝データ源の乗り換えで何を失ったか）がちょうど見えなくなる。

### 対策案

- 打ち切り時に落選記録へ `stage="actual_timeout"` の行を書く
- ドロップ候補レビューがこの段階も測定対象に含める

## 6. Yahoo系コードの削除には順序の依存がある（MEDIUM）

`hawkeye/scout/verify.py`（Yahoo再取得）と `hawkeye/marketdata/yahoo_earnings.py`
は EW一本足では役目を失う。ただし**ガイダンスの物差し**（翌四半期のコンセンサス
`next_quarter_eps_avg` / `next_quarter_revenue_avg`）は、いま Yahoo の
`hawkeye/marketdata/consensus.py` からしか来ていない
（`shift_after_print`、`hawkeye/scout/scout.py:256`）。

**先に verify.py / Yahoo を消すと、ガイダンスの柱が丸ごと沈黙する。**
順序は「EWサマリから将来コンセンサスを読む（未着手項目3）」→「Yahoo削除」。

## 7. 一度も書かれない欄（MEDIUM）

- `EarningsPrint.revenue_xbrl` / `revenue_release` — 発表文の読み取り結果を
  折り込む処理（`hawkeye/scout/release.py:127-135`）はEPSしか書いておらず、
  売上の2欄は**本番コードから一度も書かれたことがない**。
  ところが売上の実績を決める処理（`revenue_actual`）はこの2つを優先して見る
  ため、実質「Finnhubの売上しか使われない」状態
- EW移行後は `revenue_whispers`（または案Bの読み取りリスト）が主になるので、
  この2欄を**埋めるのか削るのか**を決める必要がある

## 8. `kind`（事前登録 / 事後再構成）の判定（MEDIUM）

EWカレンダー（`/api/caldata/{YYYYMMDD}`）からの事前登録を `pre_registered`、
`epsdetails` からの事後取得を `reconstructed` とする案は妥当。ただし
**EWの `epsdetails` は実績とコンセンサスを同じ応答で返す**ため、事後取得の
コンセンサスは「発表後にEWが表示している当期コンセンサス」になる。

**EWが発表後にコンセンサス値を書き換えるかは未検証。** 書き換えるなら
事後再構成の値は事前の予想ではなくなり、`reconstructed` というラベルの
「弱い証拠」という意味づけが正しく効く。書き換えないなら実は強い証拠。
どちらでも動作は安全側だが、**未検証であることを記録しておく必要がある**。

---

## 9. 重複排除が証拠の強さを見ない（LOW）

コンセンサスの重複判定（`content_key()`）は `kind` を除いている。数値が同じなら
書かない設計なので、**弱い証拠（事後再構成）が先に入っていると、後から来た
強い証拠（事前登録）が「同じ数値だから」と捨てられ、行のラベルは弱いまま残る**。

実運用では事前登録が先に走るので発火しにくいが、EW一本足では事前登録と
事後取得が同じソースの同じ数値になるため、**これまでより一致しやすくなる**。
`content_key()` に `kind` を含めるか、事前登録が来たら上書きではなく追記するかを
決めておきたい（append-onlyなので追記のみ可）。

2. **深さ `verified` の定義変更＋保留行を書かない仕様の固定**（所見3）

所見4（IPO直後銘柄）は実測とユーザー判断が要るので、この列に入れず並行で測る。

# ケース別の情報源仕様（2026-08-06）

「どの情報を、どこから、どのケースで取るか」を1枚にしたもの。実装順を決める前に
これを固定する。**この表が仕様であり、コードはこれを機械的に強制する。**

## 前提: いま実装されているもの / いないもの

| 何 | 状態 |
| --- | --- |
| EWの銘柄別 `GET /api/epsdetails/{TICKER}` | **実装済み**（`WhispersSource.details()`） |
| EWの日別カレンダー `GET /api/caldata/{YYYYMMDD}` | **未実装。** 読み取りコードが無い |
| Finnhubの決算カレンダー（予定＋過去の実績） | 実装済み |
| Yahooのコンセンサス分布・実績 | 実装済み（EW移行で廃止予定） |
| 48時間の保留 | ロジックは実装済み、**scoutに未配線** |

EWカレンダーは**過去日を引けない**（発表済みの会社が応答から消える）ため、
**「誰がいつ決算を出すか」の予定一覧は今後もFinnhubが唯一の源**。これは確定。

## A. 決算実績（EPS・売上）

| ケース | 取得元 | 出所ラベル | 四半期の扱い | 審査時の対応 |
| --- | --- | --- | --- | --- |
| **A-1: EWが当期のレコードを返す** | EW `epsdetails` | `whispers` | EWの `quarter_end` から確定 | 通常どおり。サプライズ＝実績÷コンセンサス（自前計算）。**EW自身のサプライズ値は使わない**（物差しがWhisper比とコンセンサス比で混在するため。記録のみ） |
| **A-2: EWが前期のレコードを返す**（`previous_quarter`） | 取得できず | — | 未確定 | **保留**。今日の15枠に入れない。次回走査で再読。発表から48時間で打ち切り |
| **A-3: EWにこの会社の記録が無い**（`no_record`／HTTP 204。IPO直後の典型） | 取得できず | — | 未確定 | **保留**。48時間で打ち切り。**Finnhubに実績があってもフォールバックしない**（下記の原則） |
| **A-4: EWの応答は当期だがEPSが空**（`eps_actual_missing`） | 取得できず | — | 確定はできる | 保留。A-2/A-3と同じ扱い |
| **A-5: EWが応答しない**（HTTP失敗） | 取得できず | — | — | **「実績なし」ではなく「不明」。** 保留の試行回数にも数えない（`WhispersUnavailable` は例外。会社についての事実ではなく接続についての事実） |
| **A-6: 発表文が読まれた** | 発表文（人／エージェント） | `release` | 既存行を引き継ぐ | 発表文の確定値が**常に最優先**。EWの値より強い（唯一、一次資料が背後にある読み） |

### 原則: 実績とコンセンサスは同じソースの組でしか比率を取らない

A-3で「Finnhubの実績を使えばIPO直後も拾える」と考えたくなるが、これは
**物差しのすり替えになる。** EWのコンセンサスは非GAAP（調整後）ベースが基本で、
Finnhubの実績がどのベースかは銘柄ごとに違う。分子と分母のベースが違う比率は、
数字としては出るが意味が無い。前セッションでEW自身のサプライズ値を審査から
外したのと**まったく同じ理由**。

したがってフォールバックを認めるとしても、それは
「Finnhubの実績 ÷ **Finnhubの**コンセンサス」の組でのみ成立し、出所ラベルは
`finnhub` で統一され、レポートと審理ブリーフに「この銘柄だけ別のソースで測った」と
明記される必要がある。**採否は実測後に判断**（所見4）。

さらに、**ガイダンスはEWのサマリ文からしか取れない**（無料で構造化された出所が
他に無い）。EW以外のソースで拾った銘柄は、物差しが違うだけでなく**3本柱の1本が
構造的に空のまま**審理に入る。しかもその空白はデータの穴によるもので、会社の
実態ではない。同じ土俵で順位付けする根拠が無い。

同じ理由で **Finviz は採らない**（2026-08-06 調査）。サプライズ率しか出さず実績と
予想が分離できないうえ、ガイダンスも無い。詳細は `docs/knowledge/REJECTED.ja.md`。

| **B-3: 事前登録が無いまま決算が来た** | EW `epsdetails` の当期コンセンサス | `whispers` | `reconstructed` | 弱い証拠として使う。**EWが発表後にこの値を書き換えるかは未検証**（所見8） |

### B-2をどうするか（要判断）

EWカレンダーに載らない約17%の銘柄について、選択肢は2つ:

- **(i) Finnhubの予想でも事前登録する** — 事前登録の網羅性は保たれるが、
  A-1（EWの実績）と組み合わせると**物差しの混在**になる。原則に反する
- **(ii) EWカレンダーに無い銘柄は事前登録しない** — 原則は守れるが、
  対象銘柄が17%減る。ただしその銘柄も B-3（事後再構成）で審査自体は可能

**私の推奨は (ii)。** 理由: (i) は上の原則を事前登録側から破ることになり、
「A-3ではフォールバックしないのにB-2ではする」という一貫しない規則になる。
(ii) なら、EWに載らない銘柄は一律「事後再構成の弱い証拠で審査する」に揃う。

## 10. EWは実績を後から改訂することがある（HIGH・新規）

ADEAは同じ決算（2026-08-05発表・2026-Q2）のまま、**実績EPSだけが翌日に
$0.34 → $0.42（+24%）に変わった**（売上は不変）。標本10件中1件、確定済み決算
6件のうち1件。詳細は `docs/knowledge/MEASUREMENTS.ja.md`。

これは設計に直接効く:

- **決算行は追記のみで書き換えられない。** 早く読んだ $0.34 を記録すると、
  同じ深さでは訂正できない
- サプライズ比が丸ごと変わる。$0.34 と $0.42 では上振れ・下振れが反転しうる
- **48時間の保留は「実績が届くまで待つ」規則であって「実績が動かなくなるまで待つ」
  規則ではない。** 届いた直後に読むほど改訂を踏みやすい

### 対策の方向（要判断）

- (a) 実績を読んだ後、一定時間おいて**もう一度読み、一致したら確定**とする。
  深さの階段に「暫定」と「確定」を分ける
- (b) 現状のまま記録し、改訂が起きたら**新しい深さの行として追記**する
  （追記型の設計と素直に噛み合う）。ただし「どちらが正しいか」の規則が要る
- (c) 何もしない。改訂の発生率を測ってから決める

**まず発生率を測るべき**（(c)から入る）。標本が小さすぎて頻度が分からない。

## 11. 走査レポートにEW取得結果の一覧を必ず出す（【決定 2026-08-06】）

ユーザー依頼。**審理の結果がPassでもBuyでも、毎回**、その回にEWから取得した
銘柄群を一覧で出す。目的は**ユーザーがデータを正しく取れているか毎回検証できる
ようにすること**で、判断材料ではなく点検表。

### 載せる列

| 列 | 内容 |
| --- | --- |
| ティッカー / 発表日 / 四半期ラベル | ラベルの取り違え（所見2）がここで目視で見つかる |
| EPS 実績 / コンセンサス / **サプライズ比（自前計算）** | |
| 売上 実績 / コンセンサス / **サプライズ比（自前計算）** | |
| ガイダンス 値 / 物差し（翌四半期 or 通期コンセンサス）/ 比 | 期間が比較不能なら理由 |
| EW自身のサプライズ / その基準（whisper比 or コンセンサス比） | 自前計算との差が見える。**審査には使っていない**ことを明記 |
| 取得できなかった項目とその理由 | §8.2 の告知と同じ理由コード |

### 実装上の注意

- **レポート生成コード側で出す**（`hawkeye/reports/`）。エージェントの手順書に
  「書いてください」と頼む形にしない。頼む形では書き忘れが起きるうえ、
  API modeとsession modeで出力が変わる
- 空でも「該当なし」と明示する
- 一覧はスコアの根拠ではなく**点検用**なので、順位とは独立に全件出す
