# ポートフォリオ掲載用エントリ

就活用ポートフォリオへの掲載を想定した、本プロジェクトの要約。
他プロジェクト（pergram 等）と同じ粒度・同じ書式で揃えている。

2バージョンある。**A が既定**（投資も開発も知らない読み手を想定）。
B は相手がエンジニアで、技術的な深さを見せたい場合のみ差し替える。

**書くときの前提**: このプロジェクトの目的は「年率50%のリターンを出すこと」
（`docs/design/MASTER_OVERVIEW.ja.md` §1「最終目標」、`README.md` "Target: 50%
annualized return"）。反証プロセス・監査証跡・自己採点はいずれもその**手段**
であって、目的ではない。ドクトリンにある「50%に届かなくても較正された記録は
資産である」は、**目標を外したときの評価基準**を述べた但し書きであり、これを
狙いとして書くと目的と手段が入れ替わる。

## A. 平易版（既定・非エンジニア向け）

### 🦅 Hawkeye ― 年率50%を狙う米国株の銘柄発掘・投資判断システム

目的は**「勝てる銘柄を見つけて、実際に資産を増やすこと」**。年平均50%（月あたり約3.4%）を目標に置き、そこから逆算して「同時に最大8銘柄・1銘柄あたり月+1.7%」「勝率55%、勝つときの利益は負けるときの損失の2倍」という必要条件を先に算出し、**その数字を満たさない取引は機械的に弾く**設計にしている。ただし人間が一人でこれをやると必ず失敗する——自分の見立てに都合の良い材料ばかり集め、損切りができず、外れた予想は忘れる。そこで1銘柄ごとに賛成役・反対役・判定役の3つのAIに議論させ、判断の根拠と結果を全部記録し、**勝ち方を毎回検証しながら精度を上げていく**構造にした。判断ルールそのものの設計、システム全体の設計、AIに実装させるときの仕様書と禁止事項の策定までを担当し、コードを書く作業はAI（Claude Code）に任せる体制で構築している。

- **目標から逆算した数字を、感情を挟まずに強制する**：「儲かりそう」という文章がどれだけ説得力を持っていても、それだけでは買わせない。買う前に損切り価格・利益目標・保有期限を必ず数値で登録させ、**勝ったときの利益が負けたときの損失の2倍以上ないもの、期待できる利益が+5%に届かないものは、AIの結論に関係なく自動で却下**する。1銘柄に資産の10%まで、同時に8銘柄まで、1回の失敗で失う額は資産の0.75%まで、という上限も機械が持っている。個人投資家が最も金を失う「損切りできない」「勝ち筋のない銘柄に賭ける」を、意思の力ではなく計算で潰している。

- **賛成役・反対役・判定役に、それぞれ違うものしか見せない**：同じ銘柄について、賛成役のAIは「買うべき理由」だけを書く。反対役のAIはその文章だけを読んで潰しにかかる。判定役のAIは両者の記録だけを読んで結論を出す。肝は、**賛成役には反対意見が最後まで一切見えない**こと。人間の会議では「上司が乗り気だから強くは反対しづらい」といった忖度が必ず混じり、ダメな銘柄が生き残ってしまう。互いの存在を知らないAIに書かせればそれが起きず、筋の悪い銘柄が早い段階で落ちるので、資金を本当に勝てる銘柄に集中できる。

- **AIへの指示は"お願い"でしかないので、出てきた結論を機械で検査し直す**：AIに「重大な反論には必ず答えてから買い判断を出せ」と指示しても、守る保証はどこにもない。そこで判定役の結論をプログラムで後から検査し、答え残しがあれば買い判断を機械的に取り消している。ここで実際に不具合も出した——当初は「反論の文章がそのままコピーされているか」で照合していたため、判定役が自分の言葉で言い換えて的確に反論すると"未回答"と誤判定され、**買うべき銘柄が黙って捨てられていた**。反論1件ずつに背番号を振り、番号で照合する方式に変えて解決している。

- **数字を読み取らせるAIには、答え合わせの基準を見せない**：決算発表の文章から「会社が自分で示した今後の見通し」を読み取らせる工程がある。このとき読み取り役のAIには、市場の予想値を一切渡さない。**基準を先に見せた時点で、AIはそれを超えるように文章を解釈してしまう**からだ。さらに、AIが「ここにこう書いてありました」と示した引用文が、本当に元の文章に一字一句存在するかを機械で照合し、見つからなければ回答ごと捨てる。銘柄選びの土台になる数字が捏造されれば、その先の判断は全部無意味になるので、ここは最も厳しくしている。

- **儲かった＝正しかった、とは数えない**：判断のたびに「何が、いつまでに、何%の確率で起きるか」を先に宣言させ、期限が来たら当たったかを機械的に判定する。そのうえで「儲かったか」と「予想が当たったか」を別々に採点し、**予想は外れたのに儲かったケースを"成功"ではなく"警報"として扱う**。運で勝った手法をそのまま強化すると次に大きく負けるからで、儲け続けるにはここを取り違えないことが要る。judgment の記録は上書き禁止・追記のみで、各行に直前の行の"封印"が入っており、後から「そもそもこういうつもりだった」と言い直すことを技術的に不可能にしてある。

- **実際に見つけた致命的欠陥の例**：運用してみると、判断した19件が**全て「見送り」**になった。買いが1件も出ないということは、リターンがゼロで目標が構造的に達成不可能ということ。原因を追うと「反対役の主張の方が説得力があれば見送り」というルールがあり、反対役はいくらでも懸念を出せるので永久に買えない設計になっていた。このルールを廃止し「損益の見込みが基準を超えているか」という数字の判定に一本化した。加えて、有望株を並べる順番も壊れていた——会計上の利益がほぼゼロの会社ではわずかな上振れが「予想比 +6958%」と表示され、そういう会社ばかりが上位を独占して、本当に good な決算を出した銘柄が調査対象から押し出されていた。基準額が小さすぎる会社を対象外にして是正している。

## B. 技術版（エンジニア向け・差し替え用）

### 🦅 Hawkeye ― 年率50%を目標に据えた、反証プロセス駆動の銘柄発掘・投資判断システム

年平均50%（月+3.4%）という目標から必要条件を逆算し（同時8ポジション・4週間保有でポジション月+1.7%、勝率55%、リワード/リスク2倍）、**それを満たさない取引を決定的なコードで機械的に却下する**ことを中核に据えた、米国株カタリスト投資の意思決定システム。説得力のある文章ではなく期待値で買う順序を強制するために、1銘柄を Bull / Adversary / Judge の3役に争わせ、事前登録・改ざん検知・事後採点で回す。投資ドクトリン（判断基準の成文化）、システム全体設計、AIエージェントへの要件定義・禁止事項・検収基準の策定までを担当し、実装はタスク受付ゲート（8項目の仕様が埋まるまで着手させない運用）を通して Claude Code に駆動させる体制で構築。Python / SQLite、テスト850件が外部APIを一切叩かず11.7秒で完走する。

- **目標リターンから逆算した数値を、決定的なコードが拒否権として保持**：リワード/リスク比 2.0 未満、シナリオ加重期待値 +5% 未満、損切り幅20%超、1銘柄10%超、同時8ポジション超、1トレードのリスク0.75%超は、Judge が BUY を出していても `build_position_plan()` が却下し理由を記録に追記する。判断基準の数値は全て `config.py` の1箇所に集約し、ルール変更を「コミットとして残る差分」に限定した。

- **強気役・反証役・裁定役の情報遮断を「技術境界」として実装**：Bull（強気の主張だけを作る役）・Adversary（その主張だけを見て反論する役）・Judge（記録だけを見て裁定する役）に渡す情報の切り出しを1つの関数に集約し、API方式では互いに文脈を共有しない3つのステートレス呼び出しとして実現。一方 Claude Code セッション方式では、オーケストレーター自身が全役のファイルにアクセスできるため隔離が運用規律に留まる。この差を「現行アーキテクチャでは修正不可能な制約」として設計書に明記し、直すのではなく正直に開示する判断を取った。

- **プロンプトで課したルールを、コードで再検算する二重化**：「深刻度4以上の反論に応答していない BUY は無効」という規則を、裁定役への指示とは独立にコード側でも機械的に検査し、違反すれば BUY を PASS に書き換える。当初この判定は指摘文の先頭60文字の部分一致で行っており、裁定役が自分の言葉で的確に反論すると文字列が一致せず、**正しい BUY が黙って却下されていた**。反論1件ごとに内容ハッシュのIDを付与し、ID一致で判定する方式へ変更して言い換え耐性を確保している。

- **抽出AIに「答え合わせの対象」を見せない設計＋4段のハルシネーション検証**：決算文から会社自身の来期見通しや上振れ理由を読み取らせる工程で、抽出役にはコンセンサスもサプライズ率も渡さない（超えるべき基準を見せた時点で、それは抽出ではなく作文になるため）。そのうえで「引用が原文に一字一句存在するか」「引用元が正しい文か（前期見通し文・アナリスト予想文からの引用は無効）」「単位が明記されているか」「対象期間が報告四半期と一致しているか」の4検証を通らない限り、AIの出力はデータモデルに到達しない。LLM出力は例外なくパーサ層で正規化（確率のクランプ・シナリオ確率の再正規化・未知enumのフォールバック）してから型付きモデルに入れる。

- **事前登録の不変性をDBレベルで担保し、勝ちを「実力／運」で分解**：推奨レコードは書き換え禁止、以後の事象は追記専用の日誌に記録し、各行が直前行のハッシュを含むハッシュ連鎖で改ざんを検知可能にした。決算実績・コンセンサス予想は SQLite のトリガーで UPDATE / DELETE 自体を拒否し、訂正は「新しい行を追加し古い行を無効として残す」方式に限定。そのうえで全仮説に確率と期限を事前登録させ、Brier スコア（申告確率の較正度）と、損益×仮説の正誤による4象限で採点し、**「仮説は外れたのに儲かった」を成功ではなく警報として扱う**。運で勝った手法を強化すると次に大きく負けるため。

- **リターン目標に対する自己監査と、その反映**：審理実績19件が全件 PASS ＝ BUY ゼロ ＝ リターン構造的にゼロ、という致命的欠陥を検知。「反証役の主張が強気役より説得力があれば PASS」という弁論の勝敗ルールが原因と特定し、撤廃して期待値と確信度の下限（0.55→0.65）に一本化した。候補の並び順を決めるサプライズ率が、会計上の利益がほぼゼロの銘柄で +6958% と発散して上位を占拠し、良い決算が調査対象から押し出されていた問題も、分母の絶対値による足切りで是正。さらに現行パラメータのままでは理論上限が目標ぎりぎりで実際は年率15%前後に留まりうると自己監査し、試行回数・利益の伸ばし方・リスク量の3点を未装着の課題として明示している。
