# ポートフォリオ掲載用エントリ

就活用ポートフォリオへの掲載を想定した、本プロジェクトの要約。
他プロジェクト（pergram 等）と同じ粒度・同じ書式で揃えている。

2バージョンある。**A が既定**（投資も開発も知らない読み手を想定）。
B は相手がエンジニアで、技術的な深さを見せたい場合のみ差し替える。

---

## A. 平易版（既定・非エンジニア向け）

### 🦅 Hawkeye ― AI同士に議論させて投資判断を下すシステム

株を買うかどうかを、3つのAIに「賛成役・反対役・判定役」を割り振って議論させ、その結論と根拠を後から検証できる形で記録し続けるシステム。狙いは「儲かる株を当てること」そのものではなく、**その判断が実力だったのか、たまたま運が良かっただけなのかを、後から誰でも確かめられる状態を作ること**に置いている。人は自分の失敗を都合よく忘れる生き物で、外れた予想は記憶から消え、儲かれば自分の実力だと思い込む。それを人間の心がけではなく仕組みで防ぐのが主眼。判断ルールそのものの設計、システム全体の設計、AIに実装させるときの仕様書と「やってはいけないことの一覧」の策定までを担当し、コードを書く作業自体はAI（Claude Code）に任せる体制で構築している。

- **賛成役・反対役・判定役に、それぞれ違うものしか見せない**：同じ銘柄について、賛成役のAIは「買うべき理由」だけを書く。反対役のAIはその文章だけを読んで潰しにかかる。判定役のAIは両者の記録だけを読んで結論を出す。肝は、**賛成役には反対意見が最後まで一切見えない**こと。人間の会議では「上司が乗り気だから強くは反対しづらい」といった忖度が必ず混じるが、互いの存在を知らないAIに書かせればそれが起きない。しかもこれを「そういう約束にする」のではなく、そもそも他の役の文章がファイルとして手元に渡らない作りにしてある。

- **AIへの指示は"お願い"でしかないので、出てきた結論を機械で検査し直す**：AIに「重大な反論には必ず答えてから買い判断を出せ」と指示しても、守る保証はどこにもない。そこで判定役の結論をプログラムで後から検査し、答え残しがあれば買い判断を機械的に取り消している。ここで実際に不具合も出した——当初は「反論の文章がそのままコピーされているか」で照合していたため、判定役が自分の言葉で言い換えて的確に反論すると"未回答"と誤判定され、**正しい買い判断が黙って消えていた**。反論1件ずつに背番号を振り、番号で照合する方式に変えて解決している。

- **数字を読み取らせるAIには、答え合わせの基準を見せない**：決算発表の文章から「会社が自分で示した今後の見通し」を読み取らせる工程がある。このとき読み取り役のAIには、市場の予想値を一切渡さない。**基準を先に見せた時点で、AIはそれを超えるように文章を解釈してしまう**からだ。さらに、AIが「ここにこう書いてありました」と示した引用文が、本当に元の文章に一字一句存在するかを機械で照合し、見つからなければ回答ごと捨てる。AIが実在しない内容をもっともらしく書いてしまう事故を、これで塞いでいる。

- **一度下した判断は、後から書き換えられない**：「なぜ買うと決めたか」の記録は上書き禁止で、その後に起きたことは全て後ろに書き足していく方式にした。加えて記録の各行には直前の行の"封印"が埋め込まれており、途中の1文字でも書き換えると封印が合わなくなって検知できる。人が一番やりがちな「うまくいかなかったとき、そもそもこういうつもりだったと後から言い直す」を、技術的に不可能にするのが目的。

- **儲かった＝正しかった、とは数えない**：判断のたびに「何が、いつまでに、何%の確率で起きるか」を先に宣言させ、期限が来たら当たったかを機械的に判定する。そのうえで「儲かったか」と「予想が当たったか」を別々に採点し、**予想は外れたのに儲かったケースを"成功"ではなく"警報"として扱う**。運で勝った回数が多いということは、その手法が次は通用しないという意味なので、祝わずに原因を調べる対象にしている。

- **実際に見つけた設計ミスの例**：運用してみると、判断した19件が全て「見送り」になった。原因を追うと「反対役の主張の方が説得力があれば見送り」というルールがあり、反対役はいくらでも懸念を出せるので**構造的に永久に買えない**設計になっていた。このルールを廃止し、「損益の見込みが基準を超えているか」という数字の判定に一本化した。もう一つ、有望株を並べる順番が壊れていた件もある——会計上の利益がほぼゼロの会社だと、わずかな上振れでも「予想比 +6958%」という数字が出てしまい、そういう会社ばかりが上位を独占していた。基準となる金額が小さすぎる会社を対象外にして是正している。

## B. 技術版（エンジニア向け・差し替え用）

### 🦅 Hawkeye ― 反証プロセス駆動の投資判断システム

「儲かる銘柄を当てる」のではなく「その判断が実力だったのか運だったのかを、後から third party が検証できる形で残す」ことに徹した、米国株カタリスト投資の意思決定システム。投資ドクトリン（判断基準の成文化）、システム全体設計、AIエージェントへの要件定義・禁止事項・検収基準の策定までを担当し、実装はタスク受付ゲート（8項目の仕様が埋まるまで着手させない運用）を通して Claude Code に駆動させる体制で構築。Python / SQLite、テスト850件が外部APIを一切叩かず11.7秒で完走する。

- **強気役・反証役・裁定役の情報遮断を「技術境界」として実装**：1銘柄を Bull（強気の主張だけを作る役）・Adversary（その主張だけを見て反論する役）・Judge（記録だけを見て裁定する役）の3つのAIに争わせる構成。各役が見てよい情報の切り出しを1つの関数に集約し、API方式では互いに一切の文脈を共有しない3つのステートレス呼び出しとして実現した。一方 Claude Code セッション方式では、オーケストレーター自身が全役のファイルにアクセスできるため隔離が運用規律に留まる。この差を「現行アーキテクチャでは修正不可能な制約」として設計書に明記し、直すのではなく正直に開示する判断を取った。

- **プロンプトで課したルールを、コードで再検算する二重化**：「深刻度4以上の反論に応答していない BUY は無効」という規則を、裁定役への指示とは独立にコード側でも機械的に検査し、違反すれば BUY を PASS に書き換える。当初この判定は指摘文の先頭60文字の部分一致で行っており、裁定役が自分の言葉で的確に反論すると文字列が一致せず、正しい BUY が黙って却下されていた。反論1件ごとに内容ハッシュのIDを付与し、ID一致で判定する方式へ変更して言い換え耐性を確保している。

- **抽出AIに「答え合わせの対象」を見せない設計＋4段のハルシネーション検証**：決算文から会社自身の来期見通しや上振れ理由を読み取らせる工程で、抽出役にはコンセンサスもサプライズ率も渡さない（超えるべき基準を見せた時点で、それは抽出ではなく作文になるため）。そのうえで「引用が原文に一字一句存在するか」「引用元が正しい文か（前期見通し文・アナリスト予想文からの引用は無効）」「単位が明記されているか」「対象期間が報告四半期と一致しているか」の4検証を通らない限り、AIの出力はデータモデルに到達しない。LLM出力は例外なくパーサ層で正規化（確率のクランプ・シナリオ確率の再正規化・未知enumのフォールバック）してから型付きモデルに入れる。

- **事前登録した判断の不変性を、DBレベルで担保**：推奨レコードは書き換え禁止とし、以後に起きたことはすべて追記専用の日誌に記録。各行が直前行のハッシュを含むハッシュ連鎖になっており、後からの改ざんを検知できる。決算実績・コンセンサス予想のテーブルは SQLite のトリガーで UPDATE / DELETE 自体を拒否し、数値の訂正は「新しい行を追加し、古い行を無効として残す」方式に限定した（順位を付けた時点でどの数値を見ていたかが消えると、事後検証そのものが成立しないため）。

- **勝敗ではなく「実力／運」の4象限で自己採点**：すべての仮説に確率と期限を事前登録させ、期限到来時に機械的に正誤判定して Brier スコア（申告確率がどれだけ較正されているかの指標）を算出。損益×仮説の正誤で4象限に分類し、**「仮説は外れたのに儲かった（運による勝ち）」を成功ではなく警報として扱う**。成功指標を P&L ではなく「実力による勝ちの比率」と「申告確率の実測頻度への収束」に置いている。

- **仮説修正の実例**：審理実績19件が全件 PASS という異常を、「反証役の主張が強気役より説得力があれば PASS」という弁論の勝敗で決めるルールが原因と特定。深刻な反論を監視条件に転換してもなお天秤に残り続ける構造だったため、当該ルールを撤廃し期待値と確信度の下限（0.55→0.65）に一本化した。同様に、候補の並び順を決めていたサプライズ率が、会計上の利益がほぼゼロになる REIT で +6958% と発散して上位を占拠していた問題も、分母の絶対値による足切りで是正している。数値の根拠は全て実測日・標本数付きで別ファイルに記録し、「測っていない数字は根拠に使わない」ことを規約化した。
