## 目的

### この工程が最終的に何のためにあるか

`hawkeye rank`（走査した銘柄に点数を付け、順位を決めて台帳に記録する工程）は、
**その日に見つかった数十件の決算のうち、どれを審理（強気役・反論役・判定役の
3役が1銘柄を争う工程）に送るかを決める**。審理に送られた銘柄だけがUserの前に
並び、Userはそれを見て実際に金を出すか決める。**順位が変われば、Userが買うか
検討する銘柄そのものが変わる。**

点数は5本の柱で決まる: EPS・売上・**会社の見通し（ガイダンス）**・囁き予想・
決算当日の値動き。このうち見通しだけは、走査の処理の中からAIを呼べないため、
`scout`（走査）と `rank`（採点）の**間**に別工程で読む設計になっている
（`hawkeye guidance queue` / `submit`）。

### 何が無いか

**`hawkeye rank` は、その読み取りが済んでいるかを一切確認しない。**

採点工程の関数全体（`hawkeye/cli.py` の `cmd_rank`）で `return` は2箇所しかない:

- `return 1` — 順位付け待ちの走査そのものが無いとき
- `return 0` — 最後

読み取り待ちが何件残っていても、`rank` はそのまま採点し、順位を確定し、台帳に
記録する。**止まりもしないし、警告も出さない。**

### 放置した場合に困ること

読み取りを飛ばして `rank` すると、**見通しの点数が全銘柄ゼロのまま順位が決まる**。
2026-08-18の実測では、FLXSは見通しが着いた瞬間に点数が **17.99 → 22.99（＋28%）**
動いた。全銘柄がこの分を失えば、順位は入れ替わる。

順位が入れ替われば、**審理に送られる銘柄の顔ぶれが変わり、Userの前に並ぶ銘柄が
変わる。** これは表示の問題ではなく、Userが何を検討するかが変わるという意味で
金銭判断に直接効く。

`CLAUDE.md` の不変条件6は「データが欠けているときは『未検証』として扱い、黙って
通してはならない」と定めている。台帳への記録自体は正直で（読んでいない見通しは
「未読」として残る）、数字を捏造してはいない。**壊れているのは記録ではなく、
1本の柱が全銘柄ゼロのまま誰にも止められずUserの手前まで進む経路のほうである。**

### 既にある仕組みと、それでも足りない理由

読み取り漏れを防ぐ案内は既に2つあり、どちらも正しく動いている:

- `hawkeye scout` の最終行: 「会社の見通しの読み取り待ちが**N件**あります。
  `hawkeye guidance queue` で読み切ってから `hawkeye rank` を実行してください。」
- `hawkeye guidance queue`（引数なし）: 「ガイダンスの読み取り待ちはありません。」

**どちらも人間が読んで従うことを前提にした案内であって、機械的な歯止めではない。**
`CLAUDE.md` の不変条件3は「プロンプトが求めることはコードで強制する」と定めて
いる。手順書が求めている順序が、コードで担保されていない。

### 拒否か、フラグ要求か —— 拒否を選んだ理由（タスク本文が実装時に決めよと指定した点）

**既定は拒否（終了コード1）にした。** 理由は3つ。

1. **警告して進む実装では、いま既にある2つの案内と同じものが1つ増えるだけになる。**
   `hawkeye scout` の最終行も `hawkeye guidance queue` も、既に読み取り待ちの件数を
   正しく伝えている。それでも読み飛ばしは起きうるので、足りないのは「もう一度言う」
   ことではなく「進ませない」ことである。
2. **やり直しの代償がほぼ無い。** 拒否は設定を読む前・台帳に書く前に起きるので、
   走査結果は `var/scan/pending.json` に丸ごと残る。読み取りを終えてから
   `hawkeye rank` を打ち直せば、同じ走査がそのまま採点される（実測: 拒否の直後も
   `pending.json` は残り、`scans` テーブルは0行のまま）。**取り返しのつかない副作用が
   無い側に倒すのが安いほう。**
3. **`CLAUDE.md` 不変条件6（データが欠けているときは黙って通さない）の既定は
   fail-closed 側である。**

逃げ道 `--allow-unread-guidance` を用意したのは、機械検査に繰り返し落ちる回答が
ありうるため。**逃げ道を通ったことは画面と台帳の両方に残す** —— 台帳側は走査記録の
`params` に3つの値を書く（`ranked_with_unread_guidance` / `guidance_unread_at_rank` /
`guidance_unread_tickers`）。この3つは**読み取りが済んでいる回にも 0 / False / [] を
必ず書く**。値が異常時にしか現れないと、「その回は正常だった」と「その項目が無かった
頃の古い記録」が見分けられなくなるため。

## 付録: 当初案（点検表の作り直し）を落とした理由

当初は「`hawkeye rank` が出す取得データ点検表が、読み取り済みの見通しを常に
『未読(AI待ち)』と表示する」ことを直すタスクとして登録した。実測もある——
CRGO・FLXS両方を読み終えた直後の画面で「ガイダンスを読んだ読み手: なし」
「ガイダンスが未読のまま: **2件**」と出た。同じ実行の数秒後に出した
`hawkeye report scan` は同じFLXSを「開示あり / 22.99」と正しく表示している。

落とした理由は3つ。

1. **この表を読む運用が定義されていない。** `/hawkeye-run` の手順書
   （`.claude/skills/hawkeye-run/SKILL.md`）を検索して「点検表」「inspection」
   「monitor-csv」のヒットは0件。Userに見せるよう指示されているのは
   `hawkeye report scan` のほうである。
2. **読み取り漏れの案内は他にあり、そちらは壊れていない**（上記「既にある仕組み」）。
   点検表は同じ情報を採点工程で重複表示しており、その重複が間違っている。
   一次情報が正しい以上、失われている検出能力は無い。
3. **修正の代償が釣り合わない。** 点検表を組むには生の決算イベントが要るが、
   `pending.json` に保存されているのは組み上がった表だけで、生のイベントは
   捨てられている。作り直すには保存形式を変える（既存の未記録走査が読めなく
   なる恐れ）か、集計を二重に持つ（必ずずれる）かのどちらかで、**今正しく
   動いている台帳側を壊すリスク**を負う。

矛盾そのものは、見出しに「走査時点の状態」と書けば記述として解消する。表が
「今」を語るのをやめれば嘘ではなくなるため、その1行だけを変更範囲に残した。
