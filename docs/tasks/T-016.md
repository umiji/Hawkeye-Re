## 目的

### この点検表が最終的に何のためにあるか

`hawkeye rank`（走査した銘柄に点数を付け、台帳に記録する工程）は、実行のたびに
「取得データ点検表」を画面に出す。これは順位や採否そのものではなく、**その回の
データが正しく取れているかを運用者が目で確かめるための検査シート**である。
表の冒頭にもそう書いてある:

```
この表は、**この回のデータが正しく取れているかを目視で確認するための点検表**です。
```

運用者はこれを読んで「この回の走査は、審理（強気役・反論役・判定役の3役が1銘柄を
争う工程）に銘柄を送ってよい状態か」を判断する。送られた銘柄はUserの前に並び、
Userはそれを見て実際に金を出すか決める。**この検査シートは、そこへ至る前の
最後の目視点検である。**

### 何が起きているか

検査シートのうち、**会社の来期見通し（ガイダンス）に関する欄と集計が、読み取りを
済ませた直後でも常に「未読」と表示される。**

2026-08-18の実出力（原文ママ）。CRGO・FLXSの見通しを両方とも読み終え、その直後に
`hawkeye rank` を実行した画面:

```
| CRGO | 2026-08-17 | 2026-Q2 | 決算カレンダー | ... | 未読(AI待ち) | 入口ゲートで落選 |
| FLXS | 2026-08-17 | 2026-Q4 | 決算専門サイト | ... | 未読(AI待ち) | 入口ゲートで落選 |

- ガイダンスを読んだ読み手: なし(この回はガイダンスを1件も読んでいません)
- ガイダンスが未読のまま: **2件**
```

同じ実行の数秒後に出した `hawkeye report scan`（台帳から組み直す報告）は、同じ
FLXSについて「ガイダンス: **開示あり**」「点数 22.99」と正しく表示する。
**同じ1回の実行から出た2つの出力が、同じ銘柄について矛盾している。**

### 原因

点検表は `hawkeye scout`（走査）の時点で組み立てられ、`var/scan/pending.json` に
表そのものが丸ごと保存される（`hawkeye/scout/scan_store.py` の `inspection` キー）。
`hawkeye rank` はそれを読み直してそのまま印刷している。

再採点を行う処理（`hawkeye/scout/scout.py` の `rerank_after_guidance()`）は、
候補の判定（`candidate.quality`）と点数（`candidate.score`）だけを更新し、
**点検表は作り直さない。**

そして見通しの読み取りは、**設計上かならず走査と採点の間に行われる**（走査の
処理の中からAIを呼べないため、`scout` → `guidance queue`/`submit` → `rank` の順に
分かれている）。したがってこの表は、セッションモードでは**構造上いつも「未読」**
と出る。たまたま出る不整合ではない。

古くなるのは見通しの欄だけではない。保存される行（`InspectionRow`）は
`guidance_status` / `guidance_pct` / `guidance_flags` / `guidance_excerpt` /
`guidance_extractor` / `guidance_extractor_model` に加えて `verdict`（決算判定）と
`score`（点数）も持っており、これらも走査時点の値のまま凍結される。

### 放置した場合に困ること

**1つ目（本命）: 「見通しの読み取りをやり忘れた」という実在の失敗を、この検査
シートが二度と検出できない。** 読み取りを飛ばして `rank` すると、全銘柄の見通しの
点数がゼロのまま順位が決まり、**審理に送られる銘柄の顔ぶれが変わる**。2026-08-18の
実測では、FLXSは見通しが着いた瞬間に点数が 17.99 → 22.99（＋28%）動いた。
順位が変われば、Userの前に並ぶ銘柄が変わる。その取り違えを止めるための検査シートが、
やってもやらなくても同じ文字を出す。**常に鳴る警報は警報ではない。**

**2つ目: 検査シート全体が信用されなくなる。** 運用者は数秒後に出る正しい報告と
矛盾する表を読むことになる。片方が嘘だと分かった検査シートは、他の欄——決算専門
サイトが数字を出せなかった件数、カレンダーが矛盾する行を返した件数——まで
読み飛ばされる。それらは実際に効いている検査である。

**誰にとっての問題か、正直な範囲**: 影響を受けるのは `/hawkeye-run` を回す運用者
（統括セッションと開発者）であって、最終報告を読むUserではない。台帳に記録される
値は正しく（`screened_candidates` 走査番号2: FLXS 22.99/`disclosed`）、Userに
提示される `hawkeye report scan` の出力も正しい。**現時点で金銭判断そのものは
歪んでいない。失われているのは、歪みを検出する計器のほうである。**

## 変更範囲

- `hawkeye/scout/scout.py` — `rerank_after_guidance()` が、再採点した候補の内容を
  点検表の該当行にも反映し、集計（`InspectionCounts` の `guidance_unread` /
  `guidance_declined_scope_qualified` / `readers`）を数え直す。あるいは同等の
  処理を呼び出し側（`cmd_rank`）に置く。どちらにするかは実装時に決め、理由を
  証拠欄に書く。
- `hawkeye/scout/inspection.py` — 既存行を再採点後の判定で更新するための関数を
  追加する場合のみ。判定ロジックそのものは変えない。
- `tests/` — 上記の単体テストと、`rank` の出力に対する回帰テスト。

**元の走査時点の状態を残すかどうかも、このタスクで決める。** 「走査直後は未読
だった」という事実は、読み取り漏れの追跡に使える情報である。捨てるなら捨てる
理由を、残すなら表のどこに出すかを、証拠欄に書くこと。

## 禁止事項

- **点数・順位・入口ゲートの判定ロジックに手を入れない。** 台帳に記録される値は
  現状すでに正しい。直すのは表示だけである。
- **`hawkeye scout` が出す点検表を変えない。** 走査直後の時点では「未読」は正しい
  記述である。`--monitor-csv` が書き出すCSVも走査時点のものであり、これも正しい。
- **集計の分類リストを新しく作らない。** 既存の `InspectionCounts` と
  `EarningsQuality` のフラグを使う。二重管理は必ずずれる。
- **表の列を増やさない。** T-014が決めた列構成を変えるのは別タスクの範囲。
- **仕様が不明な点を推測で埋めない。**

## 完了条件

① 見通しの読み取りを済ませてから `hawkeye rank` を実行したとき、点検表の

   ついて同じガイダンス状態を示すことを、両方の実出力を並べて示す
④ 見通しを**読まずに** `hawkeye rank` した場合は、従来どおり「未読」と表示され、
   件数が実際の未読数と一致することを確認するテストが成功する（警報が鳴るべき
   ときに鳴ることの確認。①だけでは「常に読んだと表示する」実装でも通ってしまう）
