# T-016: 見通しの読み取り漏れのまま採点・記録が進むのを止める

**2026-08-18 登録直後に範囲を縮小した。** 当初は「採点工程が出す点検表を、
読み取り後の状態で作り直す」という表の修正タスクとして登録した。その直後に
「表を直す必要があるのか」を確認したところ、**表を読む運用が定義されていない**
一方で、**読み取り漏れを機械的に止める仕組みが1つも無い**ことが分かった。
表の作り直しは範囲から外し、禁止事項に移した。経緯は「## 付録: 当初案を
落とした理由」に残す。

## 目的

### この工程が最終的に何のためにあるか

`hawkeye rank`（走査した銘柄に点数を付け、順位を決めて台帳に記録する工程）は、
**その日に見つかった数十件の決算のうち、どれを審理（強気役・反論役・判定役の
3役が1銘柄を争う工程）に送るかを決める**。審理に送られた銘柄だけがUserの前に
並び、Userはそれを見て実際に金を出すか決める。**順位が変われば、Userが買うか
検討する銘柄そのものが変わる。**

点数は5本の柱で決まる: EPS・売上・**会社の見通し（ガイダンス）**・囁き予想・
決算当日の値動き。このうち見通しだけは、走査の処理の中からAIを呼べないため、
`scout`（走査）と `rank`（採点）の**間**に別工程で読む設計になっている
（`hawkeye guidance queue` / `submit`）。

### 何が無いか

**`hawkeye rank` は、その読み取りが済んでいるかを一切確認しない。**

採点工程の関数全体（`hawkeye/cli.py` の `cmd_rank`）で `return` は2箇所しかない:

- `return 1` — 順位付け待ちの走査そのものが無いとき
- `return 0` — 最後

読み取り待ちが何件残っていても、`rank` はそのまま採点し、順位を確定し、台帳に
記録する。**止まりもしないし、警告も出さない。**

### 放置した場合に困ること

読み取りを飛ばして `rank` すると、**見通しの点数が全銘柄ゼロのまま順位が決まる**。
2026-08-18の実測では、FLXSは見通しが着いた瞬間に点数が **17.99 → 22.99（＋28%）**
動いた。全銘柄がこの分を失えば、順位は入れ替わる。

順位が入れ替われば、**審理に送られる銘柄の顔ぶれが変わり、Userの前に並ぶ銘柄が
変わる。** これは表示の問題ではなく、Userが何を検討するかが変わるという意味で
金銭判断に直接効く。

`CLAUDE.md` の不変条件6は「データが欠けているときは『未検証』として扱い、黙って
通してはならない」と定めている。台帳への記録自体は正直で（読んでいない見通しは
「未読」として残る）、数字を捏造してはいない。**壊れているのは記録ではなく、
1本の柱が全銘柄ゼロのまま誰にも止められずUserの手前まで進む経路のほうである。**

### 既にある仕組みと、それでも足りない理由

読み取り漏れを防ぐ案内は既に2つあり、どちらも正しく動いている:

- `hawkeye scout` の最終行: 「会社の見通しの読み取り待ちが**N件**あります。
  `hawkeye guidance queue` で読み切ってから `hawkeye rank` を実行してください。」
- `hawkeye guidance queue`（引数なし）: 「ガイダンスの読み取り待ちはありません。」

**どちらも人間が読んで従うことを前提にした案内であって、機械的な歯止めではない。**
`CLAUDE.md` の不変条件3は「プロンプトが求めることはコードで強制する」と定めて
いる。手順書が求めている順序が、コードで担保されていない。

## 変更範囲

- `hawkeye/cli.py` の `cmd_rank` — 採点を始める前に、見通しの読み取り待ち件数を
  確認する。残っている場合の挙動（拒否するか、明示のフラグを要求するか）は
  実装時に決め、理由を証拠欄に書く。**必ず読み切れるとは限らない**（機械検査に
  繰り返し落ちる回答がありうる）ため、絶対に進めない実装にすると運用が詰まる。
  逃げ道を用意し、その逃げ道を通ったことが台帳と画面の両方に残るようにする。
- `hawkeye/reports/monitor_ja.py` — 点検表の見出しに「走査時点の状態」である旨を
  1行加える。表が「今」を語るのをやめれば、`hawkeye report scan` との矛盾は
  記述として解消する。**表の中身・列・集計は変えない。**
- `tests/` — 上記の単体テストと、`rank` の出力に対する回帰テスト。

## 禁止事項

- **点検表を作り直さない。** 走査時点で組み立てて `var/scan/pending.json` に
  保存された表を、採点後の値で再構築する実装は、このタスクでは行わない
  （理由は付録）。保存ファイルの形式にも触らない。
- **点数・順位・入口ゲートの判定ロジックに手を入れない。** 台帳に記録される値は
  現状すでに正しい。
- **`hawkeye scout` の出力を変えない。** 走査直後の「未読」は正しい記述であり、
  `--monitor-csv` が書き出すCSVも走査時点のもので正しい。
- **見通しの読み取り工程そのもの（`guidance queue` / `submit`）に触らない。**
  T-015で直したばかりであり、正しく動いている。
- **読み取りを自動で代行しない。** `rank` がAIを呼んで読み取りを埋める実装は
  禁止。走査系の処理からAIを呼ばないのがこの設計の前提である。
- **仕様が不明な点を推測で埋めない。**

## 完了条件

① 見通しの読み取り待ちを**残したまま** `hawkeye rank` を実行したとき、待ち件数を
   名指しした上で採点を進めないことを、**実コマンドの出力で**示す
② ①の状態から逃げ道（明示のフラグ等）を使って実行したとき、採点は進むが、
   「見通しを読まずに順位を決めた」ことが画面に出て、かつ台帳の走査記録にも
   残ることを実出力で示す
③ 読み取りを済ませてから `hawkeye rank` を実行したとき、①の停止が起きず、
   従来どおり採点・記録が完了することを実出力で示す（正常系が塞がっていない確認）
④ 点検表の見出しに「走査時点の状態」である旨が出ることを実出力で示す
⑤ `.venv\Scripts\python.exe -m pytest -q` が全件成功する（着手前961件＋新規分）

①②③は実データが要る。**2026-08-18の走査データを再利用して実施する**
（使い捨て台帳）。走査をやり直さないこと——費用がかかるうえ、この検証には不要。
実施するのは本タスクの実装者。

## テスト方法

- **単体（オフライン）**: 完了条件①②③④に対応するもの。特に③（読み切った後は
  止まらない）は必須——①だけでは「常に止まる」実装でも通ってしまう。
- **回帰**: 既存全テスト。点数・順位・ゲート判定の期待値は1つも変えない。
  既存の `rank` を呼ぶテストが、読み取り待ちを残したまま実行していて新たに
  失敗する場合、**テストの期待値を書き換えて通すのではなく**、そのテストが
  どちらの経路を意図していたかを判断して直す。
- **実環境確認**: 完了条件①〜④。実装者が使い捨て台帳で実施する。

## 停止条件

- `CLAUDE.md` の共通停止条件。
- 既存テストの多くが「読み取り待ちを残したまま `rank` する」前提で書かれていた
  場合。それは仕様の解釈が割れている証拠なので、書き換える前にUserに報告する。
- 逃げ道の設計（何を残せば「黙って通していない」と言えるか）が決められない場合。
- 点検表の見出し1行を変えるだけで、`hawkeye report scan` 側との整合が取れない
  ことが分かった場合。

## 付録: 当初案（点検表の作り直し）を落とした理由

当初は「`hawkeye rank` が出す取得データ点検表が、読み取り済みの見通しを常に
『未読(AI待ち)』と表示する」ことを直すタスクとして登録した。実測もある——
CRGO・FLXS両方を読み終えた直後の画面で「ガイダンスを読んだ読み手: なし」
「ガイダンスが未読のまま: **2件**」と出た。同じ実行の数秒後に出した
`hawkeye report scan` は同じFLXSを「開示あり / 22.99」と正しく表示している。

落とした理由は3つ。

1. **この表を読む運用が定義されていない。** `/hawkeye-run` の手順書
   （`.claude/skills/hawkeye-run/SKILL.md`）を検索して「点検表」「inspection」
   「monitor-csv」のヒットは0件。Userに見せるよう指示されているのは
   `hawkeye report scan` のほうである。
2. **読み取り漏れの案内は他にあり、そちらは壊れていない**（上記「既にある仕組み」）。
   点検表は同じ情報を採点工程で重複表示しており、その重複が間違っている。
   一次情報が正しい以上、失われている検出能力は無い。
3. **修正の代償が釣り合わない。** 点検表を組むには生の決算イベントが要るが、
   `pending.json` に保存されているのは組み上がった表だけで、生のイベントは
   捨てられている。作り直すには保存形式を変える（既存の未記録走査が読めなく
   なる恐れ）か、集計を二重に持つ（必ずずれる）かのどちらかで、**今正しく
   動いている台帳側を壊すリスク**を負う。

矛盾そのものは、見出しに「走査時点の状態」と書けば記述として解消する。表が
「今」を語るのをやめれば嘘ではなくなるため、その1行だけを変更範囲に残した。
