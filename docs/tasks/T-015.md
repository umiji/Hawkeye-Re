## 目的

### この工程が最終的に何のためにあるか

Hawkeyeは、EPSが大きく上振れた銘柄を毎日数十件見つける。その上振れには意味が正反対の2通りがある
——**一時的な要因（税効果・資産売却益・和解金）**か、**本業で稼いだ利益率**か。数字だけを見ても
区別が付かない。区別が付かないまま審理（強気役 Bull・反論役 Adversary・判定役 Judge の3役が1銘柄を
争う工程）に送ると、3役はそこを推測で埋め、Userはその推測混じりの推奨を読んで実際に金を出すか
決めることになる。**この区別を会社自身の言葉から取ってくるのが、本タスクが守ろうとしている工程で
ある。**

### AIが働く5か所と、指示文の渡り方

1銘柄を判断し終えるまでに、AIに文章を読ませる場面が5つある。

| 仕事 | 誰がやるか | 指示文（＝役割・禁止事項・回答形式を書いた文章）の渡り方 |
|---|---|---|
| 決算発表文から該当箇所を**写す** | Gemini（`gemini-3.5-flash-lite`） | `hawkeye/marketdata/gemini.py` からプログラムが直接送る ✅ |
| 会社の**来期の見通しを判定する** | 使い捨てのClaudeセッション | **渡らない** ❌ |
| **一時要因か本業かを判定する** | 使い捨てのClaudeセッション | **渡らない** ❌ |
| 強気役 | 使い捨てのClaudeセッション | `bull.system.md` としてファイルに出る ✅ |
| 反論役 | 使い捨てのClaudeセッション | `adversary.system.md` ✅ |
| 判定役 | 使い捨てのClaudeセッション | `judge.system.md` ✅ |

Geminiは問題ない。審理3役も問題ない。**判定を任せる2工程だけが、指示文を受け取っていない。**

### 欠陥1: 指示文が出ないので、統括セッションが毎回自作している

`hawkeye case step`（審理を1手進めるコマンド）は指示文をファイルに書き出すので、統括セッションは
中身をそのまま貼るだけでよく、文章を考える余地が無い。ところが
`hawkeye cause queue --case-id <id>` が出すのは、読ませる文章と依頼1行だけである。
2026-08-18の実出力の末尾:

```
Report what THIS COMPANY said explains the quarter above, quoting the words
you read it from. If the summary states no reason, say so.
```

**回答形式も、許される単位の種類も含まれない。** 正しい指示文は
`hawkeye/scout/cause_agent.py` の `CAUSE_SYSTEM` と `hawkeye/scout/guidance_agent.py` の
`GUIDANCE_SYSTEM` に実在し、有料APIキーで直接呼ぶ経路でだけ読み手に渡っている。その中には
こう書かれている:

```
- If the company put a NUMBER on it, report that number and state its UNIT:
  "per_share", "million", "billion", or "percent".
```

### 欠陥2: 却下と同時に材料が消え、取り直せない

**2026-08-18の実害**: 統括セッションが単位を `pct` と書いた（正解は `percent`）。AMBQの読み取りは
`magnitude_unit_missing` として却下された。`cmd_cause_submit` は却下の経路でも
`cause_case.discard()` を呼ぶため staged パッケージが消え、**AMBQはその走査では二度と読めなく
なった**。同日の検証はMSGEに切り替えて続行した。

### 放置した場合に困ること

**1つ目（金銭判断に直接効く）**: 読み取りが落ちた銘柄が審理に行くと、3役への資料には
「理由は未確認。一時要因も税効果も利益率改善も主張するな」という注記だけが載る。3役は決算の数字
だけで買う・買わないを述べ、Userはその推奨を読む。2026-08-18のMSGEでは、この一文が資料に載った
ことで反論役が致命的攻撃を2件出し、判定役が見送りにした（`docs/tasks/T-013.md` 証拠欄）。
**同じ銘柄でも、読み取りが落ちれば結論は変わりうる。**

**2つ目（比較可能性）**: 指示文が走査ごと・統括セッションごとに変わるため、同じ抜粋でも結果が
揃わない。`CLAUDE.md` invariant 4 が求める「両エンジンが同じ定数を読むことによる比較可能性」が
成り立たない。

**3つ目（原因が見えない）**: 失敗は「読み手が失敗した」（`reader_failed`）としか記録されず、
原因が統括セッションの書いた指示文にあったことは表に出ない。

## 禁止事項

- **指示文を新しく書き起こさない。** 渡すのは既存の `CAUSE_SYSTEM` / `GUIDANCE_SYSTEM`
  そのもの。APIキー経路とセッション経路で違う文章を読ませることが、この欠陥の正体である。
- **「理由が無かった」という正当な回答でパッケージを残さない。** 残すのは機械検査を通らな
  かった場合（`reader_failed`）と呼び出し自体が失敗した場合（`call_failed`）だけ。
  `explained: false` は正常で頻出の答えであり、言い換えて再試行させてはならない
  （`.claude/skills/hawkeye-run/SKILL.md` の既存規律）。
- **却下理由の分類リストを新しく作らない。** `cause_agent.py` / `guidance_agent.py` の
  `_FAILURE_KIND` と `failure_kind()` を使う。二重管理は必ずずれる。
- **検査（引用照合・単位・期間）を緩めない。** 今回の欠陥は検査ではなく指示文の受け渡しにある。
- **Gemini側（`hawkeye/marketdata/gemini.py`）に触らない。** 写す工程は正しく動いている。
- **順位付けの点数計算・入口ゲートの判定に手を入れない。**

### ファイルは case ごとのサブディレクトリに置いた（タスク記載からの逸脱、意図的）

タスク本文は `<id>.system.md` と書いていたが、実装は
`cause/<case_id>/cause.system.md` にした。理由: 読み取り待ちを探す処理
（`list_cases()`）は `cau_*.json` というパターンでファイルを拾うため、
`cau_x.schema.json` を case ファイルの隣に置くと、**それが「もう1社が読み取り
待ち」として数えられてしまう**。審理3役の実装（`hawkeye/tribunal/casefile.py`）
も case ごとのサブディレクトリを使っており、そちらに揃えた。
`tests/test_reader_packages.py::test_a_staged_package_is_not_mistaken_for_another_waiting_case`
がこの点を固定している。
